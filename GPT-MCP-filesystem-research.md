# 1. Разбор присланных репозиториев

## `playcations/FileSystem-MCP-for-GPT`: использовать нельзя

Проект решает задачу самым опасным способом: поднимает доступный через SSE HTTP-сервер, рекомендует выставлять его через ngrok и одновременно предоставляет MCP-инструмент `shell`, который запускает произвольные команды через `subprocess.run`. Полноценной аутентификации в сервере нет, CORS разрешён для любого origin, присутствуют операции записи и рекурсивного удаления.

Дополнительно ограничение путей реализовано через строковую проверку вида `absolute_path.startswith(allowed_directory)`. Это классическая ошибка проверки префикса: при разрешённой папке `/Users/USER/Documents/case` соседний путь `/Users/USER/Documents/case-secret` также начинается с той же строки. Использование `Path.resolve()` само по себе эту ошибку не исправляет.

Практическое следствие:

* публичный endpoint фактически превращается в **удалённое выполнение команд с правами локального пользователя**;
* удалённая сторона получает не только файлы разрешённой папки, но потенциально весь объём прав процесса;
* удаление некоторых переменных окружения не является песочницей;
* добавление простого API-ключа проблему не решит, поскольку остаются `shell`, дефектная проверка путей и слишком большая поверхность атаки.

**Вердикт: не ставить даже для эксперимента на машине с рабочими или личными данными.**

---

## `jeswin/mcpfs`: технологически лучше, но публичная установка небезопасна

У этого проекта значительно лучше базовая инженерия:

* Streamable HTTP вместо самодельного SSE;
* OAuth 2.1 и PKCE;
* нормализация и `realpath`-проверки;
* более корректная обработка симлинков;
* атомарная запись через временный файл и `rename`;
* аннотации read-only/destructive для MCP-инструментов.

Но статический анализ исходников выявляет две критические проблемы.

### 1. OAuth фактически не ограничивает круг пользователей

Публичный endpoint динамической регистрации клиентов выдаёт любому обратившемуся `client_id` и `client_secret`. После этого endpoint выдачи токенов принимает grant `client_credentials` с только что созданными реквизитами. Получается следующая последовательность:

1. посторонний пользователь регистрирует своего OAuth-клиента;
2. получает secret;
3. запрашивает access token через `client_credentials`;
4. получает доступ к файловому MCP.

PKCE здесь не помогает: он защищает передачу authorization code, но не устанавливает личность владельца компьютера. Более того, consent-страница проекта сама не требует входа владельца. Хранилище клиентов, кодов и токенов находится в памяти и исчезает после перезапуска.

### 2. MCP-клиент может расширить доступ за пределы первоначальной папки

При получении MCP roots проект проверяет только то, что присланный путь существует и является каталогом, после чего заменяет им первоначальный список `allowedDirectories`. Пересечения с каталогами, заданными при запуске сервера, нет. Авторизованный клиент потенциально может прислать корень домашнего каталога или `/` и расширить область доступа.

**Вердикт:** среди двух проектов этот лучше, но выставлять его в интернет через обычный Cloudflare Tunnel в текущем виде нельзя.

Чтобы сделать его приемлемым, пришлось бы:

1. убрать публичную динамическую регистрацию либо ввести allowlist клиентов;
2. удалить `client_credentials` для произвольно зарегистрированных клиентов;
3. подключить настоящий OIDC-провайдер с идентификацией конкретного пользователя;
4. пересекать полученные MCP roots с неизменяемым первоначальным allowlist;
5. запускать сервер в контейнере с единственной смонтированной папкой;
6. не публиковать его непосредственно в интернет, а использовать Secure MCP Tunnel.

После этих изменений большая часть собственного HTTP/OAuth-кода проекта становится просто ненужной.

# 2. Какие ещё варианты существуют

## 1. `@modelcontextprotocol/server-filesystem`

Это официальный reference-сервер организации Model Context Protocol. Текущая npm-версия — **2026.7.10**, пакет имеет около **373 тысяч загрузок в неделю**. Он предоставляет чтение текстовых и бинарных файлов, получение дерева каталогов, поиск файлов, метаданные, а также операции записи и редактирования. Все инструменты снабжены MCP-аннотациями, позволяющими отличать чтение от потенциально разрушительных действий. ([npm][2])

Собственного HTTP-сервера ему не требуется: OpenAI Secure MCP Tunnel умеет самостоятельно запускать локальный stdio MCP как дочерний процесс.

Это мой основной выбор.

## 2. `j0hanz/filesystem-mcp`

Наиболее сильный сторонний вариант из найденных. Поддерживает stdio и Streamable HTTP, защиту от path traversal и выхода через симлинки, denylist чувствительных файлов, Bearer token, Host validation, структурированные ответы, diff/patch/hash и пакетные операции. Текущая npm-версия — 1.19.1. ([npm][3])

Он подходит, когда нужны расширенные инструменты — например, патчи, контрольные суммы или более строгие лимиты. Однако пакет поддерживает один небольшой сторонний проект, а число его установок на несколько порядков меньше официального сервера. Для документов юридической фирмы цепочка доверия важнее дополнительного набора функций.

**Лучший сторонний сервер, но не лучший вариант в целом.**

## 3. `cyanheads/filesystem-mcp-server`

Поддерживает stdio и Streamable HTTP, JWT, валидацию путей и развитое журналирование. При этом у него более тяжёлая зависимостная база, а последняя npm-версия 1.0.4 опубликована около года назад. ([npm][4])

Имеет смысл для уже существующей инфраструктуры этого автора, но выигрыша перед официальным сервером через Secure MCP Tunnel нет.

## 4. `adamgivon/chatgpt-custom-mcp-for-local-files`

Специально ориентирован на ChatGPT Web: read-only, Streamable HTTP, Cloudflare Tunnel и OAuth dynamic registration. Это более разумная прямая реализация, чем два присланных проекта, но она всё равно создаёт публичную сетевую поверхность и требует доверять собственному OAuth-коду небольшого проекта.

После появления официального OpenAI Tunnel такой подход в основном утратил практический смысл.

## 5. `rustmcp/rust-mcp-filesystem`

Есть реализация на Rust, ориентированная на производительность и небольшой расход ресурсов. ([npm][5])

Для вашей задачи скорость файловых системных вызовов не является узким местом: основное время уйдёт на передачу содержимого и обработку моделью. Поэтому меньшая зрелость и цепочка доверия важнее потенциального выигрыша в микросекундах.

# 3. Почему официальный сервер через Secure MCP Tunnel — лучший вариант

Архитектура будет выглядеть так:

```text
ChatGPT Web
      │
      │ OpenAI-hosted Secure MCP Tunnel
      │ исходящее HTTPS-соединение
      ▼
tunnel-client на вашем компьютере
      │
      │ локальный stdio
      ▼
Docker-контейнер с filesystem MCP
      │
      │ один bind mount, read-only
      ▼
~/MCP-Share-RO
```

Secure MCP Tunnel не открывает входящие порты и не создаёт публичный URL вашего сервера. Локальный `tunnel-client` сам устанавливает исходящее HTTPS-соединение с OpenAI, получает поставленные в очередь MCP-вызовы, передаёт их локальному серверу и возвращает ответы тем же путём. ChatGPT Web при этом видит обычное MCP-подключение. ([OpenAI Developers][6])

Преимущества этой схемы:

* отсутствует публичный ngrok/Cloudflare endpoint;
* не нужен собственный OAuth-сервер;
* файловый MCP вообще не слушает TCP-порт;
* нет `shell`, запуска процессов или произвольных сетевых запросов;
* контейнер не получает API-ключ туннеля;
* контейнер не имеет сети;
* внутрь контейнера монтируется только одна специально подготовленная папка;
* монтирование осуществляется на уровне Docker в режиме `readonly`;
* даже при ошибке проверки путей сервер не увидит остальную файловую систему хоста.

Последний пункт принципиален. Официальный filesystem-сервер тоже поддерживает динамические MCP roots, поэтому я не рассматриваю его внутренний allowlist как единственную security boundary. Реальной границей должен быть **контейнер с единственным bind mount**, а не JavaScript-проверка пути.

## Шаг 0. Проверить доступность функций аккаунта

Сначала проверьте:

## Шаг 1. Создать отдельную папку только для MCP

```bash
mkdir -p "$HOME/MCP-Share-RO"
chmod 700 "$HOME/MCP-Share-RO"

printf 'Проверка доступа MCP\n' > "$HOME/MCP-Share-RO/README.txt"
chmod -R go-rwx "$HOME/MCP-Share-RO"
```

Не нужно монтировать:

```text
/
$HOME
$HOME/Documents
$HOME/Library
весь iCloud Drive
весь OneDrive
весь архив юридической фирмы
папки .ssh, .config, .aws
каталоги исходного кода с .env
```

В `MCP-Share-RO` должны находиться именно **копии выбранных материалов**, а не симлинки на рабочие каталоги.

Для юридических документов разумная структура:

```text
MCP-Share-RO/
├── 00_README/
├── 10_CURRENT_MATTER/
│   ├── originals/
│   ├── extracted-md/
│   └── metadata/
└── 90_REFERENCE/
```

Не стоит одновременно помещать в одну MCP-папку материалы разных доверителей, между которыми требуется конфиденциальное разделение. Документ контрагента теоретически может содержать prompt injection, побуждающий модель прочитать другие файлы из той же доступной папки.

## Шаг 2. Собрать контейнер с закреплённой версией официального пакета

Я рекомендую не запускать `npx` непосредственно на хосте. Контейнер создаёт дополнительную границу и не передаёт MCP-серверу переменные окружения хоста.

```bash
mkdir -p "$HOME/.local/share/mcp-filesystem-image"
cd "$HOME/.local/share/mcp-filesystem-image"

cat > Dockerfile <<'EOF'
FROM node:22-bookworm-slim

ARG MCP_FS_VERSION

RUN test -n "${MCP_FS_VERSION}" \
    && npm install -g --omit=dev \
       "@modelcontextprotocol/server-filesystem@${MCP_FS_VERSION}" \
    && npm cache clean --force

ENTRYPOINT ["mcp-server-filesystem"]
EOF
```

Сборка текущей зафиксированной версии:

```bash
docker build \
  --pull \
  --no-cache \
  --build-arg MCP_FS_VERSION=2026.7.10 \
  -t local/mcp-filesystem:2026.7.10 \
  .
```

Версия `2026.7.10` является текущей на дату настоящего анализа. Обновлять её нужно осознанно, а не использовать плавающий `latest`. ([npm][2])

У Docker также есть готовый образ `mcp/filesystem`, собранный Docker Inc. из официального репозитория и подписанный через Cosign. Однако опубликованный в каталоге вариант сейчас содержит 11 инструментов, тогда как текущий npm-пакет уже имеет более новый набор, включая `read_media_file` и расширенное получение списков файлов. Поэтому собственный четырёхстрочный образ из точно закреплённой npm-версии предпочтительнее. ([Docker Hub][7])

## Шаг 3. Создать защищённый wrapper

```bash
mkdir -p "$HOME/.local/bin"

cat > "$HOME/.local/bin/mcp-filesystem-ro" <<'EOF'
#!/bin/sh
set -eu

SHARE="${HOME}/MCP-Share-RO"
IMAGE="local/mcp-filesystem:2026.7.10"

if [ ! -d "${SHARE}" ]; then
  printf 'MCP share directory not found: %s\n' "${SHARE}" >&2
  exit 1
fi

exec docker run \
  --rm \
  -i \
  --user "$(id -u):$(id -g)" \
  --network none \
  --read-only \
  --cap-drop ALL \
  --security-opt no-new-privileges \
  --pids-limit 128 \
  --memory 1g \
  --env HOME=/tmp \
  --tmpfs /tmp:rw,noexec,nosuid,size=64m \
  --mount "type=bind,src=${SHARE},dst=/data,readonly" \
  "${IMAGE}" \
  /data
EOF

chmod 700 "$HOME/.local/bin/mcp-filesystem-ro"
```

Что обеспечивают параметры:

* `--network none` — сервер вообще не может выходить в сеть;
* `--read-only` — корневая файловая система контейнера неизменяема;
* `readonly` у bind mount — рабочая папка физически доступна только для чтения;
* `--cap-drop ALL` — удаляются Linux capabilities;
* `no-new-privileges` — процесс не может повысить привилегии;
* `--user` — процесс запускается не от root;
* API-ключ туннеля внутрь контейнера не передаётся;
* `/data` — единственный каталог хоста, видимый серверу.

Проверка запуска:

```bash
"$HOME/.local/bin/mcp-filesystem-ro"
```

Нормальное поведение — процесс запустится и будет ожидать MCP-сообщения по stdin. Остановите его через `Ctrl+C`.

## Шаг 5. Создать tunnel и runtime API key

В OpenAI Platform:

1. Откройте настройки организации.
2. Перейдите в **Tunnels**.
3. Создайте tunnel.
4. Свяжите его с вашей Platform organization и персональным ChatGPT workspace.
5. Скопируйте значение вида `tunnel_...`.
6. Создайте отдельный runtime API key с разрешениями `Tunnels Read + Use`.

Не сохраняйте API key прямо в shell history. В стандартном macOS `zsh`:

```zsh
read -s "CONTROL_PLANE_API_KEY?OpenAI runtime API key: "
echo
export CONTROL_PLANE_API_KEY
```

Создайте профиль:

```bash
tunnel-client init \
  --sample sample_mcp_stdio_local \
  --profile local-files-ro \
  --tunnel-id 'tunnel_REPLACE_WITH_YOUR_ID' \
  --mcp-command "$HOME/.local/bin/mcp-filesystem-ro"
```

Проверка:

```bash
tunnel-client doctor \
  --profile local-files-ro \
  --explain
```

Запуск:

```bash
tunnel-client run \
  --profile local-files-ro
```

Во время создания приложения и при каждом последующем MCP-вызове этот процесс должен быть запущен. `tunnel-client` предоставляет локальные endpoints `/healthz`, `/readyz`, `/metrics` и `/ui`; фактический локальный адрес будет указан в выводе процесса. ([OpenAI Developers][6])

Для теста на MacBook можно предотвратить засыпание на время работы:

```bash
caffeinate -i tunnel-client run --profile local-files-ro
```

Пока `tunnel-client` работает:

1. Откройте **Settings → Apps**.
2. Включите **Developer mode**.
3. Выберите создание нового приложения.
4. В поле подключения выберите **Tunnel**.

Именно tunnel, а не локальный адрес и не URL ngrok, должен использоваться в настройке приложения. OpenAI прямо указывает, что ChatGPT не подключается к localhost непосредственно; для локальных и on-premises MCP предназначен Secure MCP Tunnel. ([OpenAI Developers][6])

## Шаг 7. Проверить границы доступа

Первый тестовый запрос:

> Используй приложение Local Files — Read Only. Сначала вызови `list_allowed_directories` и покажи результат без дополнительных действий.

Ожидаемый каталог:

```text
/data
```

Второй запрос:

> Покажи содержимое каталога `/data`.

Третий:

> Прочитай файл `/data/README.txt`.

После этого проверьте отрицательные сценарии:

* путь хоста вроде `/Users/.../Documents` не должен существовать внутри контейнера;
* запись в `/data` должна завершаться ошибкой файловой системы;
* доступ к сети из контейнера отсутствует;
* в список разрешённых путей не должны попадать каталоги хоста вне `/data`.

На Pro write-инструменты могут не быть доступны со стороны ChatGPT вообще. Если после перехода на Business/Enterprise они появятся, контейнерный `readonly` всё равно физически заблокирует запись.

# 5. Особенность PDF и DOCX

Filesystem MCP — это **не полноценный документный парсер и не RAG-индекс**.

Текущая официальная реализация:

* читает текстовые файлы как UTF-8 независимо от расширения;
* бинарные файлы возвращает через `read_media_file` в виде base64/MCP resource;
* `search_files` ищет по именам и шаблонам путей, а не по смыслу и не по полному тексту документов. ([npm][2])

Поэтому для юридической работы я бы использовал уже знакомую вам схему:

```text
PDF/DOCX
   │
   ├─ Docling
   ├─ MarkItDown
   └─ OCR для сканов
          │
          ▼
     Markdown + metadata
          │
          ▼
     MCP-Share-RO
```

Рекомендуемый состав:

```text
originals/
    contract.pdf
    court-act.docx

extracted-md/
    contract.md
    court-act.md

metadata/
    contract.json
    court-act.json
```

В metadata полезно сохранять:

* имя исходного файла;
* исходный относительный путь;
* SHA-256;
* дату модификации;
* используемый конвертер;
* наличие OCR;
* номер страницы или диапазон страниц для каждого блока.

Так ChatGPT будет получать нормальный текст, а не многомегабайтный base64 PDF. Исходники при этом можно вообще не помещать в MCP-папку, если достаточно производных Markdown-файлов.

# 6. Обязательные меры для клиентских и судебных документов

Secure MCP Tunnel защищает от публичного доступа к компьютеру, но **не означает локальную обработку содержимого**. Когда ChatGPT вызывает чтение файла, запрошенный фрагмент передаётся через tunnel в OpenAI и обрабатывается моделью. Туннель скрывает ваш MCP-сервер от интернета, но не держит прочитанное содержимое исключительно на локальной машине. ([OpenAI Developers][6])

Поэтому рабочая конфигурация должна быть следующей:

1. В MCP-папку попадают только предварительно отобранные материалы.
2. Особенно чувствительные данные предварительно обезличиваются.
3. Разные доверители или дела с различным режимом доступа не смешиваются в одном root.
4. Исходная рабочая папка никогда не монтируется напрямую.
5. Симлинки наружу не используются.
6. Серверу не предоставляются `shell`, браузер, сеть или запуск процессов.
7. Источники всегда монтируются только для чтения.

Если впоследствии понадобится сохранение результатов, лучше создать **второй отдельный MCP-контейнер** с единственной папкой вроде `~/MCP-Outbox`, доступной для записи. Исходные документы при этом должны остаться в отдельном read-only подключении. Не следует давать одному MCP одновременно читать весь архив и записывать обратно в него.

Так, ну а что мне делать, если у меня пользовательская подписка, а не корпоративная? У меня подписка Pro x20

---

**Переходить на корпоративную подписку не требуется.** В предыдущем ответе я слишком широко сформулировал ограничение.

Для личной подписки **ChatGPT Pro** доступно подключение собственных MCP-приложений в режиме разработчика, но только с операциями **чтения и получения данных**. Полный MCP с записью, изменением и удалением доступен Business и Enterprise/Edu. Для вашей задачи — дать веб-версии ChatGPT доступ к локальной папке с документами — режима чтения достаточно. ([OpenAI Help Center][1])

## Что именно доступно на личной Pro

На вашем тарифе можно:

* просматривать каталоги;
* искать файлы;
* читать содержимое файлов;
* получать метаданные;
* использовать такой MCP в обычном чате;
* использовать его в Deep Research для чтения и получения данных.

Нельзя рассчитывать на:

* запись новых файлов через MCP;
* редактирование существующих файлов;
* перемещение или удаление файлов;
* использование пользовательского MCP в Agent Mode.

Пользовательские MCP-приложения сейчас работают в **веб-версии ChatGPT**, но не на мобильных устройствах. Deep Research поддерживает их только для чтения, а Agent Mode пользовательские приложения не использует. ([OpenAI Help Center][1])

## Что меняется в ранее предложенной схеме

Архитектура остаётся прежней:

```text
ChatGPT Pro в браузере
        │
        ▼
Secure MCP Tunnel
        │
        ▼
локальный MCP-сервер
        │
        ▼
одна разрешённая папка только для чтения
```

Но вам **не нужны**:

* ChatGPT Business;
* корпоративный администратор;
* несколько пользователей или рабочих мест;
* корпоративная рабочая область;
* Enterprise-функции управления ролями.

Для личного аккаунта OpenAI прямо предусматривает использование **персональной Platform organization**, связанной с персональной рабочей областью ChatGPT. Это техническая организация в OpenAI Platform, а не корпоративная подписка ChatGPT. ([OpenAI Developers][2])

## Практический порядок действий

### 1. Включите режим разработчика в личном ChatGPT Pro

Откройте именно веб-версию ChatGPT:

```text
Настройки → Приложения → Расширенные настройки → Режим разработчика
```

В английском интерфейсе:

```text
Settings → Apps → Advanced Settings → Developer mode
```

OpenAI отдельно указывает, что пользователи Pro должны включить Developer Mode для подключения пользовательских MCP с разрешениями чтения/получения данных. ([OpenAI Help Center][1])

Если переключателя нет:

1. убедитесь, что открыта именно персональная рабочая область Pro, а не другая рабочая область;
2. используйте браузерную версию, не мобильное приложение;
3. выйдите из аккаунта и войдите снова;
4. проверьте раздел `Apps`, а не старый раздел `Connectors`;
5. при сохранении проблемы обратитесь в поддержку OpenAI.

Отсутствие переключателя не означает, что вам обязательно нужен Business: официальная документация прямо предусматривает ограниченный MCP-доступ для Pro. ([OpenAI Help Center][1])

### 2. Используйте личный аккаунт OpenAI Platform

Зайдите в OpenAI Platform под тем же аккаунтом. Там должна использоваться ваша персональная Platform organization.

В разделе управления туннелями нужно:

1. создать `tunnel_id`;
2. создать runtime API key;
3. связать туннель:

   * с персональной Platform organization;
   * с персональной рабочей областью ChatGPT.

В документации Secure MCP Tunnel специально указано, что для персональных аккаунтов используется персональная Platform organization соответствующего аккаунта. ([OpenAI Developers][2])

### 3. Оставьте файловый доступ строго только для чтения

Для вашей Pro-подписки я бы сохранил ранее предложенную конфигурацию:

* отдельная папка, например `MCP-Share-RO`;
* внутрь неё помещаются копии выбранных документов;
* Docker-контейнер;
* монтирование папки с параметром `readonly`;
* отсутствие сети у контейнера;
* никаких `shell`, `exec`, `delete`, `write_file`;
* только операции списка, поиска, чтения и получения метаданных.

Это не просто соответствует ограничениям Pro, но и является правильной моделью безопасности для юридических документов.

Даже если используемый MCP-сервер технически содержит инструменты записи, контейнерное монтирование `readonly` физически не даст ему изменить исходные документы. Однако для максимальной совместимости с Pro лучше, чтобы сервер вообще **не объявлял** инструменты записи и удаления.

### 4. Запустите Secure MCP Tunnel

Secure MCP Tunnel поддерживает персональные аккаунты и локальные MCP-серверы. Он не открывает входящий порт на вашем компьютере: локальный `tunnel-client` сам создаёт исходящее HTTPS-соединение с OpenAI и передаёт вызовы локальному MCP. ([OpenAI Developers][2])

Для запуска нужны:

* `tunnel_id`;
* runtime API key;
* локально доступный MCP-сервер — через stdio либо HTTP.

После запуска туннеля в ChatGPT нужно создать пользовательское приложение и выбрать:

```text
Connection → Tunnel
```

Затем выбрать созданный туннель или вставить его `tunnel_id`. Официальная инструкция предусматривает именно такой способ подключения из ChatGPT. ([OpenAI Developers][2])

### 5. Используйте MCP не в Agent Mode

Рабочий сценарий:

```text
Обычный чат ChatGPT Pro
или
Deep Research
        +
подключённое приложение Local Files
```

Пример запроса:

> Используй приложение Local Files. Покажи доступные каталоги, затем найди в них документы, содержащие в имени слова «отчет оценщика». Не открывай другие файлы.

После этого:

> Прочитай файл `/data/отчет-оценщика.md` и составь карту разделов со ссылками на номера страниц.

Agent Mode для этого не подходит, поскольку пользовательские MCP-приложения им сейчас не вызываются. ([OpenAI Help Center][1])

## Нужна ли отдельная оплата API

Подписка ChatGPT Pro и OpenAI Platform — это разные системы биллинга. ChatGPT Pro не включает API-использование. ([OpenAI Help Center][3])

При этом:

* наличие персональной Platform organization не означает покупку корпоративного тарифа;
* runtime API key является техническим требованием Secure MCP Tunnel;
* в документации туннеля не указан отдельный тариф непосредственно за транспорт туннеля;
* возможные расходы Platform следует контролировать отдельно от подписки Pro.

То есть покупать Business ради самого доступа к локальной папке не нужно. Но раздел Platform Billing необходимо проверить отдельно.

## Обязательная настройка конфиденциальности для юридических документов

На персональных рабочих областях Free, Plus и Pro передача данных для улучшения моделей включена по умолчанию, но её можно отключить:

```text
Настройки → Управление данными →
«Улучшать модель для всех» → выключить
```

После отключения новые разговоры не будут использоваться для обучения моделей. ([OpenAI Help Center][4])

Для работы с клиентскими материалами это следует сделать **до подключения MCP**.
