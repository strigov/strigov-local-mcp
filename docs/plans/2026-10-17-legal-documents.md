# Lawyer case folders: documents, scans and continuation

## Goal

ChatGPT web chat (GPT Pro) reads a lawyer's case folder through this read-only MCP connector without the user uploading anything. Today the server only understands UTF-8 text: PDFs, DOCX, spreadsheets, e-mails, archives and scans come back as an opaque base64 resource (≤ 15 MiB) or fail, and search and listing stop at fixed limits with no way to continue. Real case folders hold 330 MB / 979-page PDFs, scanned PDFs (JPEG/JBIG2/CCITT/JPX), Latin-only OCR garbage layers, DOCX with comments and tracked changes, 812 `.xls` + 113 `.xlsx`, koi8-r `.eml`, ZIPs with CP866 names and nested ZIPs, and 127 TIFFs.

This plan adds in-process, pure-Rust readers for those formats. Every extracted fragment names its source (logical `root/path`, archive member, page, sheet, row, paragraph or attachment) and says whether it came from a native text layer or an OCR layer embedded by another program. It separates "how big a file may be on disk" from "how big one answer may be", adds continuation cursors so large documents and folders can be read completely, and stays light: no OCR, no index, no cache, no native libraries, and the macOS sandbox stays as it is. Nobody yet knows whether ChatGPT passes images or PDF resources from a tool result to the model. An OpenAI staff reply from April 2026 says tool images are *not* a vision input path today. So Ф1 is a small experiment, and every visual feature after it branches on what the experiment finds.

## Acceptance criteria

List 3–7 externally observable criteria that define "done" for the whole plan. Reviewers may block only on these criteria, stated user requirements, repo constraints, or high-materiality risks.

- **AC1 — Experiment.** Ф1 ships a build in which `read_file` returns PNG/JPEG/GIF/WebP as MCP `image` content (always alongside a text block). It also ships a stdlib-only generator of synthetic probe files and a written procedure, `docs/chatgpt-content-experiment.md`. The user's recorded outcome (A/B/C plus size thresholds) decides Ф3's branch and the calibrated response limits.
- **AC2 — Text with provenance and continuation.** Through MCP, `read_document` returns text for PDF (text layer), DOCX, XLSX, XLS, EML, MSG and plain text. Each chunk names the logical file path, and each unit names its page / sheet+row / paragraph / mail part and its `source` (`text_layer` or `ocr_layer` for PDF). A `nextCursor` chain returns the whole document with no gaps or duplicates. A cursor for a file that has changed fails with `STALE_CURSOR`.
- **AC3 — PDF overview.** `inspect_document` on a PDF reports the page count and classifies every page as `text`, `ocr_text`, `no_text` or `empty`, with `suspicious` reasons. A Latin-only OCR layer over a scan is flagged. For a 979-page PDF this finishes within 10 s, or returns a resumable `nextCursor`.
- **AC4 — Visual access per experiment branch.** Under branch A, images and scanned PDF pages come back as MCP `image` content with the long side ≤ 2048 px and an optional `region` crop. Under branch B they come back as single-page PDF resources. Under branch C a text-only "not viewable" explanation is returned. A whole multi-page PDF is never returned. HEIC, legacy `.doc` and other unsupported inputs return explicit `UNSUPPORTED_FORMAT` errors with a hint.
- **AC5 — Containers.** ZIP members (including CP866 names stored without the UTF-8 flag, and a nested ZIP up to depth 3) and e-mail attachments can be listed (`list_directory`) and read through every reader, using `archive.zip::member` paths. Zip-bomb limits (size, ratio, entry count), unsafe member names and the existing blocked-name policy are enforced inside containers.
- **AC6 — Large folders.** `list_directory`, `search_files` and `search_text` walk in deterministic sorted order and return `nextCursor`. A folder bigger than one call's limits is covered completely across calls, with no duplicates or omissions. One exception (ledger Ф2-F5-B3, Ф2-F6-B1): an entry whose own position (root id plus its path relative to the walk base) is too long for a continuation cursor to hold (C5 position-length rule) is not listed and not descended, and the response counts it in `skippedTooDeep`, once per cursor chain. Every other entry, however deep, is walked. `search_text` also matches inside PDF/DOCX/XLSX/XLS/EML/MSG within per-call byte and time budgets and reports locators. `search_text` with `path` pointing at one document returns all matches with page/locator.
- **AC7 — Limits, safety, release.** On-disk size limits per format are decoupled from response limits (table C0) and enforced with explicit errors. On a synthetic PDF of at least 300 MiB, the text/overview path runs at peak RSS ≤ file size + 128 MiB. Every existing security test still passes, no host path appears in errors, the macOS sandbox profile is unchanged, no new files ship, and all new crates are pure Rust under MIT/Apache/BSD. Server instructions and README describe the new capabilities, and the version is 2.2.0.

## Non-goals / deferred

List explicit exclusions. Reviewers MUST classify requests for these as `REJECTED_BY_SCOPE` or `DEFER` unless the orchestrator authorizes scope expansion.

- OCR of any kind. Searching the content of images or scans.
- pdfium, MuPDF, tesseract, full PDF page rasterization (including `hayro`). Rendering vector-only or tiled PDF pages to pixels. These pages use the single-page PDF fallback or "not viewable".
- JBIG2 / JPX decoding. Under branch A these pages use the PDF fallback. Adding `hayro-jbig2`/`hayro-jpeg2000` (MSRV 1.92) is a possible follow-up, not part of this plan.
- Legacy `.doc`, `.ppt`, `.rtf` parsing (`.rtf` no longer returns raw text: read tools return `UNSUPPORTED_FORMAT` with a "save as DOCX or PDF" hint, since raw RTF escapes Cyrillic as `\'xx`), ODS/ODT, PPTX, RAR/7z/tar, HEIC/HEIF.
- Disk cache, persistent index, background indexing, write tools, network access, changes to the macOS sandbox profile.
- Reconstructing DOCX automatic list numbering. Paragraph indexes (`¶N`) are the locator. DOCX headers, footers, footnotes, endnotes and text boxes beyond inline order.
- XLSX formulas, merged cells, formatting, charts and pictures. Values are read as cached by the file.
- MSG bodies stored only as compressed RTF (reported as "body only in RTF"). Reading MSG embedded messages (`attach_method = 5`; listed, not readable). Password-protected PDF/ZIP/office files.
- Searching inside ZIP members or e-mail attachments, and file-name search inside archives. More than one match per file in folder-wide search (single-document search returns all matches).
- EXIF metadata reporting. Multi-page GIF/WebP animation frames beyond the first.
- The legacy Node/Docker server in `src/*.js`.
- A whole-load guard for lopdf PDF loading (object-stream amplification, parse amplification, cumulative stream bytes, duplicate xref offsets, encrypted files; R17). Deferred from Ф2 and revisited before Ф5, because Ф5 `search_text` parses PDFs folder-wide (ledger Ф2-F5-B2-doc).

| `MAX_DIR_ENTRIES` | 100 000 | walk.rs | Entries held and sorted per directory window. Larger directories are enumerated completely in successive name-ordered windows (C5), so per-call memory stays bounded. |
| `PDF_LIMIT` | 512 MiB | pdf.rs | With the image-content filter, peak memory on ordinary PDFs ≈ file + parsed non-image objects. This is not a bound for crafted PDFs: the lopdf load itself has no whole-load budget, so its parsed object set can be far larger than the file (known residual risk R17, ledger Ф2-F5-B2-doc). Measured on a synthetic 326 MiB / 979-page PDF: 354 MB peak RSS filtered vs 709 MB unfiltered, load 17 ms vs 50 ms (page cache warm). Covers the 330 MB real stress file with headroom. |
| `PDF_ENCRYPTED_LIMIT` | 256 MiB | pdf.rs | lopdf ignores the load filter for encrypted files (`load_encrypted_document` copies every object's raw bytes, then parses and decrypts each), so memory is about 2.1× the file. This is an accepted residual (R17, ledger Ф2-F5-B2-doc). It is bounded by this limit only when step 1 below sees the key: a trailer key spelled with `#xx` name escapes (e.g. `/Encr#79pt`, which lopdf decodes to `/Encrypt`) passes the raw pre-check, so such a file is loaded on the encrypted path up to `PDF_LIMIT` (512 MiB) before the post-load check rejects it with `FILE_TOO_LARGE` (ledger Ф2-F6-N2). Encryption is detected without a metadata preflight (C7 Loading, ledger Ф2-F5-B1): a file over this limit is refused with `FILE_TOO_LARGE` before lopdf runs if its raw bytes contain `/Encrypt`, and again after the bounded load if the loaded document is encrypted. |
| `PDF_STREAM_LIMIT` | 64 MiB | pdf.rs | `LoadOptions.max_decompressed_size` and every `*_with_limit` call on non-content streams (ToUnicode / font encodings, image streams). It is also the cumulative budget of decoded ToUnicode bytes over all fonts the text walker resolves for **one page** (C7 font-map budget): 64 MiB in total per page for font maps, not 64 MiB per stream. Page content and Form XObject content use `PDF_CONTENT_LIMIT` instead. |
| `PDF_CONTENT_LIMIT` | 2 MiB | pdf.rs | Cumulative decompressed content decoded for **one page** before lopdf `Content::decode`: all of the page's content streams plus every Form XObject content the text walker decodes (each `Do`, at every nesting depth it follows, ≤ 3), counted together. `Content::decode` costs ≈ 100× its input (measured on the release binary: 1 MiB of `0 0 m\n` → 110 MiB peak RSS, 8 MiB → 799 MiB), so this caps the content-decode part of the page-text working set at ≈ 220 MiB (font maps add ≤ ≈ 280 MiB, per-font encodings ≤ ≈ 200 MiB and glyph-decode output ≤ ≈ 56 MiB; see the `TOUNICODE_*`, `PDF_PAGE_FONT_LIMIT`, `PDF_PAGE_WORK_LIMIT` and `PDF_PAGE_GLYPH_LIMIT` rows and the per-call budget below). A page over it is not text-extracted and is flagged `contentTooLarge` (C7); the other pages read normally. |
| `TOUNICODE_CODE_LIMIT` | 65 536 codes | pdf.rs | Per font (user decision 2026-10-18). lopdf 0.45.0 `ToUnicodeCMap::from_sections` (`encodings/cmap.rs:88-143`) visits every code of every declared `bfrange`, so its cost grows with the declared ranges, not with the stream bytes, and `PDF_STREAM_LIMIT` does not cap it (measured on the release binary: a ≈ 1 KB PDF reached 276.6 MiB peak RSS with one 3-byte range and 533.8 MiB with a 4-byte range). Before lopdf parses a font's ToUnicode map, the server's own bounded scan counts the map's codes (sum of `bfrange` spans plus `bfchar` entries). A font over this limit, or whose ranges the scan cannot parse, is skipped and its glyphs count as undecodable (C7); the rest of the page reads normally. A 65 536-code map with one-unit targets costs ≈ 6–8 MiB and ≈ 4.4 ms to resolve. lopdf allows a target of up to 256 UTF-16 units (`parser/cmap_parser.rs:270-274`) and stores a copy of it for every code, so a 65 536-code map with maximal targets holds ≈ 45 MiB (ledger Ф2-F3-D1, measured below). |
| `TOUNICODE_PAGE_CODE_LIMIT` | 262 144 codes (4 × `TOUNICODE_CODE_LIMIT`) | pdf.rs | Cumulative ToUnicode codes over all fonts resolved for **one page** (page fonts plus Form XObject fonts; each font is resolved once per page, so a map shared by N fonts is charged N times). Once it is exhausted, further fonts on that page are skipped and their glyphs count as undecodable; fonts resolved earlier keep decoding. Caps the font maps held for one page at ≈ 24–32 MiB with one-unit targets and ≈ 180 MiB with maximal 256-unit targets (measured on the release binary: four 65 536-code maps with 256-u16 targets hold 178.6 MiB; ledger Ф2-F3-D1). |
| `PDF_PAGE_WORK_LIMIT` | 67 108 864 units (2^26; calibrated in Ф2 Step 11, ledger STRUCT-1-cal) | pdf.rs | Per-page work budget (ledger STRUCT-1), held in the walker's per-page `PageState` with the other per-page budgets and reset on every page. One unit is charged per content operator processed, per resource lookup step (a `/Font` or `/XObject` name looked up in a scope's dictionary, a scope's `/Font`/`/XObject` dictionary fetched, each reference hop followed), per `/Differences` element of a font being resolved, per XObject entry `page_images` visits, per decoded byte (page and Form XObject content, each ToUnicode pre-scan decode, lopdf's re-decode of an accepted map), and per UTF-16 unit of glyph-decode output a shown string may produce (ledger Ф2-F4-B1): for each `Tj`/`'`/`"` string and each `TJ` string element, its bytes × the selected font's maximum destination length (C7), charged before lopdf's `Encoding::write_to_string` allocates anything; the same charge also counts against `PDF_PAGE_GLYPH_LIMIT` (next row). A decode that fails with a non-limit error is charged its whole limit, since lopdf may have inflated that much before failing (`PDF_STREAM_LIMIT` for a ToUnicode stream). When the budget is exhausted the page stops: its text is discarded and it is flagged `content_too_large` (C7; no new field). **Value:** a full `PDF_CONTENT_LIMIT` page (2 Mi bytes + ≤ 1 Mi operators, because every operator takes ≥ 2 decoded content bytes) + its glyph output (≤ 2 Mi shown bytes, charged ≤ 2 Mi units with simple encodings and one-unit maps, and never more than `PDF_PAGE_GLYPH_LIMIT` = 4 Mi, which stops the page first) + ≈ 57–59 Mi for ordinary maps and lookups, i.e. ≈ 28–30 MiB of decoded ToUnicode maps (each accepted map is charged twice: pre-scan and lopdf's re-decode). So ordinary pages never reach it. Glyph output alone can no longer exhaust it: `PDF_PAGE_GLYPH_LIMIT` stops the page at 4 Mi units, 1/16 of this budget (> 16 KiB of bytes shown in a font with lopdf's maximal 256-unit destinations), while ordinary pages show ≤ ≈ 50 KB and real maps rarely give a glyph more than a few units. A failed ToUnicode decode is charged `PDF_STREAM_LIMIT` = 64 Mi = the whole budget, so a failed decode plus any other work (the `Tf` operator and lookup steps that lead to it are always charged first) flags the page `content_too_large`: every page with a corrupt ToUnicode stream is flagged instead of only skipping that font. Likewise a page whose ToUnicode maps total more than ≈ 28–30 MiB decoded (less half its glyph-output charge) is flagged before it reaches the 64 MiB per-page ToUnicode byte budget; no real document comes close. **Time on the target hardware** (Apple silicon Mac mini, release build). Pre-measurement estimates: decoded bytes ≈ 1–3 ns each (inflate + scan); lookup steps, `/Differences` elements and XObject entries ≈ 10–15 ns each, because C7 looks each distinct name up once per page instead of iterating dictionaries; glyph-output units ≈ 2–5 ns each (lopdf copies each target, then converts to UTF-8 through three temporary buffers), so the ≤ 4 Mi units `PDF_PAGE_GLYPH_LIMIT` allows a page take ≈ 8–21 ms. **Measured in Ф2 Step 11:** at 2^27 a page cycling `/Differences` through all 3 734 distinct valid glyph names took 3.2483 s, over 2.5 s, so per the halving rule below the value was halved to 2^26. At 2^26 the same page takes 1.6272 s and every other unit kind then charged ≤ 0.78 s. Glyph-output units were added after that calibration (ledger Ф2-F4-B1) and are measured after the fix in Step 11 (a) and (e) under the same 2.5 s rule. Before the fix they were uncharged: an 8.9 KB PDF ran one page for 8.25 s at 3 989 MiB peak RSS, unflagged. A page that exhausts the budget therefore ends in ≤ ≈ 2 s, a fifth of `SEARCH_DEADLINE`. (Round 3 measured ≈ 105 ns per font entry: 3.4 × 10^8 visits in 35.9 s. That included re-keying every `/Font` entry on every `Do`, which the cache removes.) With ordinary pages it stays ≈ 600 MB. **PDF load caveat (known residual, R17; ledger Ф2-F5-B2-doc):** these figures assume the loaded PDF's parsed objects stay near the file size, as they do for ordinary PDFs. The lopdf load of a crafted PDF is not bounded by them. Object-stream members with overlapping or duplicate offsets are each parsed and retained, parsing amplifies up to ≈ 60× (a parsed `lopdf::Object` is 120 bytes, e.g. per element of a flat array), `PDF_STREAM_LIMIT` caps each decoded stream but not their sum, duplicate xref offsets cost CPU per entry, and encrypted PDFs bypass the load filter (bounded by `PDF_ENCRYPTED_LIMIT`, or by `PDF_LIMIT` when the `/Encrypt` key is `#xx`-escaped; see that row). **Operational caveat (macOS):** libmalloc's large-allocation cache keeps freed large blocks, so the process footprint can stay far above these per-call live peaks after the call. The figures above are live-allocation peaks, not footprint. Time: search, inspect and PDF `read_document` stop at 10 s with a cursor, also inside a page (C7 deadline rule). ### C4 — Cursor (Ф2; `native/cursor.rs`)

```rust
#[derive(Clone, Copy, Debug, PartialEq, Eq)]
pub(crate) struct Fingerprint { pub size: u64, pub modified_ns: u64 }

#[derive(Clone, Copy, Debug, PartialEq, Eq)]
pub(crate) enum CursorKind { Walk, Doc, Inspect, Find }  // layout byte: 0, 1, 2, 3

#[derive(Clone, Debug, PartialEq, Eq)]
pub(crate) struct Cursor {
    pub v: u8,                       // = 1
    pub k: CursorKind,
    pub h: u64,                      // request_hash of the parameters that define the sequence
    pub f: Option<Fingerprint>,      // Doc/Inspect/Find: on-disk file; Walk (search_text folder mode): the unfinished document `p`
    pub p: Vec<String>,              // Walk: components of the last processed entry (or of the unfinished document when f is Some); first = root id
    pub u: u64,                      // Doc/Inspect/Find, and Walk with f: next unit index
    pub o: u64,                      // Doc: char offset inside unit u; Find and Walk with f: hits already returned in unit u
}
pub(crate) const CURSOR_MAX_LEN: usize = 2048;
pub(crate) fn request_hash(parts: &[&str]) -> u64;   // std::hash::DefaultHasher::new(), each part + 0xFF separator
pub(crate) fn encode(cursor: &Cursor) -> String;     // base64 URL_SAFE_NO_PAD of the binary layout below
pub(crate) fn decode(raw: &str, kind: CursorKind, hash: u64) -> crate::filesystem::Result<Cursor>; // INVALID_CURSOR on length/base64/layout/version/kind/hash mismatch
pub(crate) fn check_fingerprint(cursor: &Cursor, current: Fingerprint) -> crate::filesystem::Result<()>; // STALE_CURSOR
pub(crate) fn walk_child_fits(root_id: &str, parent: &[String], name: &str) -> bool; // C5 position-length rule: can this child's own position be encoded?
```
- **Binary layout (ledger Ф2-F5-B3; replaces JSON, whose escaping of `"`, `\` and control characters in names could push a valid walk position over `CURSOR_MAX_LEN`).** In order: byte `v` (= 1; JSON cursors were never released); byte `k` (0 Walk, 1 Doc, 2 Inspect, 3 Find); `h` as 8 bytes little-endian; one flags byte (bit 0 = `f` present, all other bits 0); if `f` is present, `size` and `modified_ns`, 8 bytes little-endian each; `u` and `o` as unsigned LEB128 varints; the component count of `p` as a varint; then each component as a varint byte length (≥ 1) followed by its raw UTF-8 bytes, with no escaping. Nothing follows the last component. Every varint uses the minimal encoding of a `u64` (≤ 10 bytes). The encoding is canonical, so equal cursors give equal strings (determinism) and `decode(encode(c)) == c`. `decode` returns `INVALID_CURSOR` for: a string over `CURSOR_MAX_LEN` (checked before base64), bad base64, truncated input, trailing bytes, an unknown `v` or `k`, set reserved flag bits, a non-minimal or overflowing varint, a component count larger than the bytes left (checked before allocating), a zero-length or non-UTF-8 component, and a `k`/`h` mismatch. Fingerprint, `STALE_CURSOR` and the deletion tolerance of walk resumes (C5) are unchanged.
- **Size.** The fixed part is ≤ 49 raw bytes (11 header bytes, 16 for `f`, ≤ 10 each for `u` and `o`, ≤ 2 for the count), and each component costs its length + 1 or 2 bytes. Base64 without padding gives ⌈4 × raw / 3⌉ characters, so a cursor fits `CURSOR_MAX_LEN` exactly when raw ≤ 1536 bytes. Doc/Inspect/Find cursors have no components (≤ 49 raw bytes). Walk cursors carry the root id (≤ 32 bytes, `config.rs`) plus the entry's components; the C5 position-length rule keeps them within 1536. `encode` `debug_assert!`s the result length ≤ `CURSOR_MAX_LEN`.
- **`walk_child_fits(root_id, parent, name)`** (ledger Ф2-F6-B1) is true iff the Walk cursor whose position is this child fits in 1536 raw bytes, with the worst case for the non-position fields: `p` = `[root_id] ++ parent ++ [name]` (the actual root id, the parent directory's components relative to the walk base, and the child's `to_string_lossy` name), `f` present, `u` = `o` = `u64::MAX`. It computes exactly the raw length `encode` would produce for that cursor (fixed part 11 + 16 + 10 + 10 bytes, the component-count varint, and varint length + bytes for each component), without allocating the cursor. So a `true` child encodes to ≤ `CURSOR_MAX_LEN` characters in every cursor kind or state the walk can later give it (Ф5 folder search adds `f`/`u`/`o`), and a `false` child could not. No name-length limit is assumed: macOS (APFS, 255 UTF-16 units per name, so up to 765 UTF-8 bytes), Linux and Windows all go through the same exact check, and the former private `MAX_NAME_BYTES` constant is removed. Examples with root id `work`: 5 nested 255-byte ASCII directories fit (1338 raw bytes) and a 6th does not (1595); two nested 255 × `я` directories (510 bytes each) fit, but a 502-byte name inside the second does not (1581); the reviewer's case (4 nested directories of 200 `"` each) costs ≤ 890 raw bytes, ≤ 1187 characters.
Hash inputs: the tool name, canonical root id (or `all`), the normalized `path` string, and `query` (search) / `startPage`,`endPage`,`sheet` (documents). `maxChars` and `limit` are *not* hashed; they may change between calls. **Rule:** cursor contents are never used to open, resolve or build a path. Walk components are only compared with names read from disk.

```rust
                      max_depth: usize, resume_after: Option<Vec<String>>, include_resume_entry: bool) -> Self;
}
impl Iterator for Walker<'_> { type Item = WalkEvent; }
```
Order is pre-order: each directory's children are sorted by `file_name().to_string_lossy()` bytes, and a directory's descendants follow it immediately. This order is lexicographic on `components`. Blocked names are never yielded. Symlinks are yielded with their type but never followed or descended. With `resume_after = Some(c)`, every entry with `components <= c` is skipped (`components < c` when `include_resume_entry` is true, so the entry equal to `c`, if it is still on disk, is yielded again; used only by the Ф5 folder search to resume an unfinished document). A directory whose `components` are `< c` and not a prefix of `c` is skipped without being read. Directories are read lazily, one sorted frame per level.
- **Windowed directory frames (bounded memory, complete coverage).** A frame never holds more than `MAX_DIR_ENTRIES` names. Reading a directory streams `read_dir` once and keeps only the `MAX_DIR_ENTRIES` smallest names strictly greater than the frame's lower bound (a bounded max-heap by name), plus a flag saying whether more qualifying names existed. The first window's lower bound is "none", or, when resuming, names `< c[level]` are excluded (`c[level]` itself is kept only to descend into it or, with `include_resume_entry`, to yield it). When a window is exhausted and the flag is set, the directory is read again with the lower bound = the last name of that window, producing the next window. Because the cursor's `p` already carries the last emitted name at every level, a resumed call rebuilds the right window the same way. Re-reads cost one extra `read_dir` per window; no index or cache is kept.
- **Position-length rule (cursor length; ledger Ф2-F5-B3, Ф2-F6-B1; replaces the earlier worst-case descent rule).** Every emitted cursor must fit `CURSOR_MAX_LEN` (C4), and any entry the walker yields may become a cursor position (`p` = `[root_id] ++ components`, as `filesystem.rs` builds it). So the check is made per child, on its actual position, and ordinary deep paths stay fully walkable:
  - *Where.* When the walker reads a directory window, it checks each child it keeps (after the blocked-name, lower-bound and resume filters, which run first; blocked names are never counted) with `cursor::walk_child_fits(root_id, &frame.components, &name)` and marks the ones that do not fit. Marked children stay in the window in name order and take window slots like any other name, so window bounds and resumed windows are built exactly as before. There is no check before reading a directory: every directory whose own entry was yielded and that the walker would descend into (a directory, not a symlink, with `depth < max_depth`) is read normally, whatever its depth. A directory none of whose children fit needs no special handling; it is read, and each child is checked and counted.
  - *What happens to a child that does not fit.* When its turn comes in pre-order it is not yielded, not stat'ed and not descended, so nothing below it is read or counted, and it never becomes the walker's or a caller's position. Its type does not matter. The walker adds 1 to a private pending count instead. The next `Entry` it yields carries that count in `skipped_before`, and the count resets. If the walk ends with a pending count > 0, the walker's last event is `TailSkipped(count)`. No event is yielded for a count of 0.
  - *Resume.* A skipped child S always lies strictly between two yielded positions in pre-order (it is never descended, so no yielded position has it as a prefix). A walk resumed from cursor `c` drops every name ≤ `c` exactly as it drops entries (the window filter excludes names `< c[level]`, the before-check skips the rest) and adds to the pending count only skipped children `> c`. So in every walk that reaches S, S is attached to the first entry yielded after it (or to `TailSkipped`), never to an entry ≤ `c`. In particular, with `include_resume_entry` the re-yielded entry equal to `c` has `skipped_before = 0`.
  - *Counting.* Callers add the `skipped_before` of each entry they process, and the `n` of each `TailSkipped(n)` they process, to `skippedTooDeep`. Every path that processes an entry and advances the call's position adds it, including the paths that count the entry as inaccessible. An event left for the next call (a budget reached before it, or `list_directory`'s final `peek`) is not counted; the next call resumes from the position before it, meets the same skipped children again and counts them when it processes that event. `TailSkipped` goes through the same budget checks as an entry, but it is not a position: it does not change the call's last position and does not count toward `WALK_LIMIT`, so a final page may carry only that count. The pending count of a walker dropped at the end of a call is discarded. So each skipped child is counted exactly once per cursor chain, and no cursor ever has to encode its position, wherever the page boundary falls relative to it.
  - A run of consecutive children that do not fit cannot hold a cursor, so the call that reaches it consumes the whole run before its next yield; this costs in-memory work plus one `read_dir` per window the run spans.
  - **`skippedTooDeep`** is an integer, always present (0 when nothing was skipped), in the responses of the three tools that walk with `Walk` cursors: `list_directory`, `search_files` and `search_text`. It means "entries (files, directories or symlinks) not listed because their path is too long for a continuation cursor; a skipped directory's contents are not visited and not counted". The server instructions and README text that describe the field use this meaning.

- **Loading (ledger Ф2-F5-B1: no metadata preflight).** Production code never calls `lopdf::Document::load_metadata_mem`: in lopdf 0.45.0 it runs with `max_decompressed_size: None` (`reader.rs:151-163`) and decodes XRef streams and object streams without a limit. Steps:
  1. Only if `bytes.len() > PDF_ENCRYPTED_LIMIT`: a raw-byte search of `bytes` for `/Encrypt` (`memchr::memmem`, already a dependency). A hit returns `FILE_TOO_LARGE` before lopdf runs. A non-encrypted file over 256 MiB that happens to contain the bytes `/Encrypt` outside compressed streams is refused too, which is accepted.
  2. `Document::load_mem_with_options(bytes, LoadOptions { filter: Some(image_filter), max_decompressed_size: Some(PDF_STREAM_LIMIT), ..Default::default() })` (set the fields on `LoadOptions::default()`). This bounded load decodes the XRef streams with the limit too. A failure that needs a password (`InvalidPassword`, `Decryption`) returns `PDF_ENCRYPTED`; any other failure returns `DOCUMENT_INVALID`.
  3. Encryption is derived from the loaded document. lopdf 0.45.0 (`reader.rs:868-930`) decrypts a file it can open with the empty user password, removes `/Encrypt` from the trailer and sets `doc.encryption_state = Some(..)`. When no password is supplied and the empty one fails, it keeps `/Encrypt` in the trailer and leaves `encryption_state` as `None`. So `encrypted = doc.encryption_state.is_some() || doc.trailer.get(b"Encrypt").is_ok()`.
  4. If `encrypted` and `bytes.len() > PDF_ENCRYPTED_LIMIT`, return `FILE_TOO_LARGE`. This re-check catches `/Encrypt` spelled with `#xx` name escapes, which step 1 misses. Otherwise, if the trailer still holds `/Encrypt` (`encryption_state` is `None`), return `PDF_ENCRYPTED`.
  `metadata()` reports this `encrypted`. Title and producer still come from the loaded `/Info`.
  `image_filter: lopdf::FilterFunc` (a plain `fn`, verified compile against lopdf 0.45.0): for `Object::Stream` whose dict `/Subtype` is `/Image` and whose id is not in a `thread_local!` keep-set, replace `content` with `vec![0]` and set dict key `LocalFilesPlaceholder = true`. For non-streams return `Some((id, object.clone()))`. `load` sets the keep-set from `keep_images` and clears it afterwards. lopdf must be compiled with `default-features = false` (no `rayon`), so the filter runs on the calling thread.
- **Text extraction** (custom walker on public lopdf APIs: `Dictionary::get_font_encoding_with_limit`, `Encoding::write_to_string`, `get_page_content_with_limit`, `content::Content::decode`, `Stream::decompressed_content_with_limit`, `Stream::get_plain_content_with_limit`, `get_page_resources`). Operators: `BT/ET`, `Tf` (selects a font handle, resolved lazily; below), `Tr` (modes 3 and 7 count as invisible), `q/Q` (save/restore the text state, ≤ `PDF_Q_DEPTH_LIMIT` saved states per content stream; a deeper `q` stops the page with `content_too_large`), `Tj`, `TJ` (number < −250 → space), `'` and `"` (newline + show), `T*`, `Td/TD` (ty ≠ 0 → newline; tx > 0 with ty = 0 → space if none), `Tm` (y change > 0.5 → newline), `Do` on a Form XObject (recurse with the form's `/Resources`, falling back to the page's, depth ≤ 3). Characters that fail to decode count toward `undecodable`; so do U+FFFD and C0 controls other than `\n\t`.
- **Per-page state, lazy resources and the work budget (ledger STRUCT-1).** One `PageState` per page is shared by the page's content and every Form XObject it follows (and by the Ф3 `page_paint` walk). It holds the content bytes left (`PDF_CONTENT_LIMIT`), the ToUnicode codes and bytes left (font-map budget, below), the work units left (`PDF_PAGE_WORK_LIMIT`), the glyph-output units left (`PDF_PAGE_GLYPH_LIMIT`, ledger Ф2-F4-B1 extension), the units charged since the last deadline check, the optional call deadline, the name caches, and the fonts table (≤ `PDF_PAGE_FONT_LIMIT` entries, with a `FontKey` → handle map of the same size). Each fonts-table entry holds the font's lopdf `Encoding` (or none, if skipped) and its maximum destination length in UTF-16 units (glyph output, below). All of it starts fresh on every page.
  - `TextState` is a small `Copy` value: `font: Option<u32>` (an interned font handle, an index into the page's fonts table), `mode`, `in_text`, `y`. It owns no name bytes, so a `q` copies a fixed ≤ 32 bytes.
  - **Lazy resolution.** The text walker never iterates a `/Font` or `/XObject` dictionary. The page's scope is its direct resources followed by its inherited ones (`get_page_resources`), searched in that order with today's precedence: for a font, the first dictionary whose `/Font` has that name resolving to a dictionary; for an XObject, the first dictionary with an `/XObject` key. A form's scope is its own `/Resources`, or else the scope it was painted from. On `Tf /N`, a per-page cache maps `(scope, N)` to a font handle. On a miss, `N` is looked up in the scope (each step charged; below). A font object is mapped through its `FontKey` (object id, or scope + name for a direct dictionary, as today) to one handle, so each font is resolved at most once per page, when it is first selected. A name that does not resolve to a font dictionary is cached as a miss, and its glyphs count as undecodable. `Do /N` uses a second `(scope, N)` cache that maps to the form stream or to none. Each cache holds one entry per distinct `(scope, name)` that occurs in decoded content, so the stored name bytes stay ≤ `PDF_CONTENT_LIMIT`.
    - **Font cap (ledger STRUCT-1 extension).** A `FontKey` already in the fonts table gets its existing handle, whatever name selected it. A new `FontKey` is entered only while the table holds fewer than `PDF_PAGE_FONT_LIMIT` fonts. Every entered font counts, including one later skipped by a font-map budget or by the hop rule below. When the table is full, the font is not resolved: nothing of it is read beyond the name lookup already charged, its `(scope, N)` is cached as a miss, and its glyphs count as undecodable. Cache entries made earlier keep their handles, so fonts resolved before the cap keep decoding. The page is not flagged. Per-font state is therefore ≤ `PDF_PAGE_FONT_LIMIT` lopdf `Encoding` values (C0 row; `/Differences` maps ≤ ≈ 0.2 MiB each, ToUnicode maps bounded by the font-map budget).
    - **Hop rule for `/Encoding` (ledger STRUCT-1 extension).** Before a newly entered font goes any further, the server follows its `/Encoding` through at most `ENCODING_HOP_LIMIT` = 8 reference hops (each charged as a lookup step). If the object after 8 hops is still a reference (a longer chain, or a cycle of any length), the font is skipped: no pre-scan, nothing handed to lopdf, glyphs undecodable. lopdf's `get_base_encoding` would follow such a chain without a hop cap and build the `/Differences` maps of a dictionary at its end, which the server would not have charged. Real files put a name, a dictionary or one reference in `/Encoding`, so this never drops a real font. Chains that end within 8 hops go on to the `/Differences` charge (below) and the pre-scan decision (font-map budget).
  - **Charging.** Each charge is taken from the work units left: 1 per content operator processed (any operator, including unknown ones); 1 per lookup step (fetching a scope's `/Font` or `/XObject` dictionary, looking a name up in it, and each reference hop followed, through a counting dereference capped at lopdf's 128 hops); before lopdf resolves a font, the length of the direct `/Differences` array of the `/Encoding` dictionary its chain ends at (the hop rule above guarantees the chain ends within `ENCODING_HOP_LIMIT` hops, so lopdf never processes an uncharged `/Differences` element; lopdf reads only a direct array, `object.rs:508`); and every decoded byte. Decoded bytes are the page content returned by `get_page_content_with_limit`, each form's decoded content, each ToUnicode pre-scan decode, and the accepted map's length again for lopdf's re-decode, charged before `get_font_encoding_with_limit`. A decode that fails with a non-limit error is charged its limit (font-map budget, below). Glyph-decode output is charged before lopdf produces it (next item).
  - **Glyph output (ledger Ф2-F4-B1).** lopdf 0.45.0 `UnicodeMapEncoding::write_to_string` (`encodings/mod.rs:84-117`) emits up to 256 UTF-16 units per code and builds three temporary buffers per call, so the decoded text of a string can be ≈ 256× its bytes and was not bounded by the content charge. `show(bytes, state, page_state: &mut PageState, out) -> PageResult<()>` is called once per `Tj`/`'`/`"` string and once per `TJ` string element. When `state.in_text` holds, before calling `write_to_string` (and before the undecodable fallback), it computes `bytes.len()` × the selected font's maximum destination length (saturating) and charges it first to the page's glyph-output units left (`PDF_PAGE_GLYPH_LIMIT`, ledger Ф2-F4-B1 extension), then through `charge()` to the work units left. Codes are ≥ 1 byte and each emits ≤ that many units (a missing code emits one U+FFFD), so the charge bounds lopdf's output. The maximum is the value the ToUnicode pre-scan recorded for a font whose map it accepted (font-map budget, below), and 1 for every other font: fonts that are not pre-scanned (lopdf uses a one-byte, `/Differences`, WinAnsi or UTF-16 simple encoding, ≤ 1 unit per byte), skipped or unresolved fonts (one U+FFFD per byte), and no selected font. If the charge exceeds the glyph-output units left or the work units left, `show` returns `PageStop::Limit`, the caller propagates it with `?`, and the page is flagged `content_too_large` through the exhaustion path below. Nothing is decoded for that string. So lopdf emits ≤ `PDF_PAGE_GLYPH_LIMIT` units per page (C0 part 4). The deadline check inside `charge()` applies too, so a deadline that passes mid-page is noticed at a shown string as well. Text outside `BT … ET` is neither charged nor decoded, as before.
  - **Exhaustion.** When a charge exceeds the units left, the page stops through the same path as the content budget: the text gathered so far is discarded and `page_text` returns `content_too_large: true`. A `q` beyond `PDF_Q_DEPTH_LIMIT` stops the page the same way. This is not an error; the other pages and the call are unaffected.
  - **`page_images`.** `page_info` runs `page_images`' traversal on the same `PageState` after the text walk, charging 1 unit per XObject entry visited. If the budget runs out there, the page is flagged `content_too_large` too. Called on its own (Ф3), `page_images` gets a fresh budget and returns `DOCUMENT_INVALID` ("page resources exceed the extraction limits") when it is exhausted.
- **Deadline rule (inside a page; ledger STRUCT-1).** `page_info_within(page, Some(deadline))` stores the deadline in the `PageState`. Whenever `PDF_DEADLINE_CHECK_UNITS` units have been charged since the last check, the walker compares `Instant::now()` with it. If the deadline has passed, the page stops, everything gathered for it is discarded, and the call returns `Ok(None)`. The page is not flagged: a page's result never depends on timing, because it is either complete or not reported. With `None` (the first page of every call, and `page_info`/`page_text`), no deadline applies and the page is bounded by `PDF_PAGE_WORK_LIMIT` (≤ ≈ 2 s, C0). This keeps the progress guarantee, and an interrupted page is extracted from scratch as the first page of the next call, so no page is lost or loops. Callers: `inspect` passes `None` for its first page and `Some(deadline)` for the following ones, and on `None` returns the pages classified so far with `next = Some(page)`. `PdfText::unit_within` maps to `page_info_within`, and `read_document` uses it per C6. Per call, wall time ≤ max(`SEARCH_DEADLINE`, load + one page) plus the C0 check overshoot.
- **Page content budget (`PDF_CONTENT_LIMIT`, per page, cumulative).** No content bytes reach `Content::decode` beyond the page's budget:
  - The page's content streams are fetched with `get_page_content_with_limit(id, PDF_CONTENT_LIMIT)` (in lopdf 0.45.0 that limit is already cumulative over all of the page's content streams, including unfiltered ones). The budget left is `PDF_CONTENT_LIMIT` minus the bytes returned.
  - Each Form XObject `Do` the walker follows (depth ≤ 3) fetches the form with `Stream::decompressed_content_with_limit(remaining)` and subtracts its decoded length from `remaining` before `Content::decode` runs on it. A form painted N times is charged N times, because it is decoded N times.
  - `Error::Decompress(DecompressError::MemoryLimitExceeded)` from either call stops the page: any text gathered so far is discarded, and `page_text` returns `Ok(PageText { text: "", visible_chars: 0, invisible_chars: 0, undecodable: 0, content_too_large: true })`. This is not an error, so `read_document`, `inspect_document` and the other pages are unaffected. Other failures keep their existing handling.
  - ToUnicode and image streams keep `PDF_STREAM_LIMIT` as their per-stream limit; their bytes do not count toward the page content budget. ToUnicode maps have their own per-page budgets (font-map budget, below).
  - The budget lives in the shared content walker, so the Ф3 `page_paint` (C9) inherits it, together with the work budget and the `q` limit. A page over any of them counts as composite there, so it is never extracted as a single image. `chars < MIN_TEXT_CHARS` gives `NoText` if the page has images, else `Empty`. Otherwise `OcrText` if `invisible_chars * 2 >= visible_chars + invisible_chars`, else `Text`. `suspicious` takes the first matching reason: `"undecodable"` if undecodable ≥ 5 % of chars; `"mojibake"` if letters in U+00C0–U+00FF are ≥ 20 % of letters; `"no_cyrillic_over_scan"` if `scan_image` and letters ≥ 40 and Cyrillic letters (U+0400–U+04FF) = 0. `scan_image` is true when any page image has `width*height ≥ SCAN_IMAGE_PIXELS`. A page with `content_too_large` is always `NoText` with no `suspicious` reason, because no text layer was read.
- **Font-map budget (ToUnicode; per font and per page, cumulative; ledger Ф2-F2-PM1).** lopdf builds a ToUnicode map by visiting every code of every declared `bfrange` (0.45.0 `encodings/cmap.rs:88-143`), so its cost is bounded by codes, not by stream bytes. Each font is resolved at most once per page, when a `Tf` first selects it, through the per-page fonts table shared by the page and its Form XObjects (≤ `PDF_PAGE_FONT_LIMIT` fonts; ledger Ф2-F2-B1, STRUCT-1). The same per-page state holds the page's two font-map budgets: codes left (starts at `TOUNICODE_PAGE_CODE_LIMIT`) and decoded ToUnicode bytes left (starts at `PDF_STREAM_LIMIT`). Both start full on every page. Every decode below is also charged to the page's work budget.
  - **Pre-scan decision (ledger STRUCT-1).** A font is pre-scanned whenever its `/ToUnicode` resolves to a stream, through `get_deref(b"ToUnicode")`, the same call lopdf makes. The only exception is when its `/Encoding` is followed by the server through at most `ENCODING_HOP_LIMIT` = 8 reference hops and ends at an encoding that lopdf would definitely use instead of the map, never reading `/ToUnicode` (lopdf 0.45.0 `object.rs:440-447, 468-543`). That is either (a) a name other than `Identity-H`/`Identity-V`, or (b) a dictionary whose `/BaseEncoding` is absent or a direct name other than `Identity-H`/`Identity-V`. Everything else that ends within 8 hops is pre-scanned: no `/Encoding`; an Identity name; an Identity or indirect `/BaseEncoding`; another object type; or a missing object. A chain still unresolved after 8 hops (longer chain or cycle) never reaches this decision: the font is skipped by the hop rule (per-page state, above). The decision never relies on `doc.dereference`, which stops at 128 hops while lopdf's `get_base_encoding` resolves longer chains (round 3: a 129-hop chain reached lopdf unscanned). Fonts that are not pre-scanned go straight to `get_font_encoding_with_limit` as before.
  - If either page budget is already exhausted, the font is skipped without decoding anything.
  - Otherwise the stream is decoded with `Stream::get_plain_content_with_limit(PDF_STREAM_LIMIT)`, the same call lopdf makes. `Error::Decompress(MemoryLimitExceeded)` here (one stream alone over `PDF_STREAM_LIMIT`) still surfaces as `DOCUMENT_INVALID`, unchanged (ledger Ф2-F1-B1). Any other decode error skips the font, and lopdf may have inflated up to `PDF_STREAM_LIMIT` before failing (e.g. `/Filter [/FlateDecode /Bogus]`). So the failure sets the page's ToUnicode bytes left to 0 and charges `PDF_STREAM_LIMIT` work units. Later pre-scanned fonts on that page are skipped without decoding, so a page makes at most one failed ToUnicode decode (ledger STRUCT-1). After a successful decode, the decoded length is charged to the page's byte budget, saturating at 0, and to the work budget. If it was more than the byte budget had left, the font is skipped. So per page, at most one stream beyond the byte budget is ever decoded.
  - The scan is one linear pass over the decoded bytes. It builds no mapping (it is not a CMap decoder; lopdf still decodes the map). Inside `beginbfchar … endbfchar` it counts one code per entry (a source hex string and its destination). Inside `beginbfrange … endbfrange` it reads `<lo> <hi>` followed by a hex-string or array destination, and adds `hi − lo + 1`. The scan cannot parse the ranges, and the font is skipped, when `lo`/`hi` are not hex strings of equal length 1–4 bytes, when `hi < lo`, when an array destination has more elements than the span, or when a section is unterminated. The sum saturates. In the same pass the scan records the map's maximum destination length in UTF-16 units (ledger Ф2-F4-B1): a hex-string destination of d hex digits counts ⌈d / 4⌉ units, at least 1. For a `bfrange` with an array destination it is the longest element. It is 1 if the map has no destination. Everything outside these sections is ignored.
  - If the total is over `TOUNICODE_CODE_LIMIT`, or over the page's codes left, the font is skipped. Otherwise the codes are charged to the page, the recorded maximum destination length is stored in the font's fonts-table entry for the glyph-output charge, and the scan buffer is dropped before `get_font_encoding_with_limit(&doc, PDF_STREAM_LIMIT)` runs (lopdf decodes the same stream again).
  - A skipped font takes the existing skipped-font path (ledger Ф2-F1-B1): it is left out of the font map, so `show()` counts its glyphs as undecodable. There is no page flag and no error. The rest of the page reads normally, including fonts resolved earlier, and the next page starts with full budgets.
  - Cost per page: lopdf maps for ≤ 262 144 codes are held (≈ 24–32 MiB with one-unit targets, ≤ ≈ 180 MiB with maximal 256-u16 targets; ≈ 18 ms to build). ToUnicode decoding is ≤ 64 MiB charged plus one overshooting stream or one failed decode ≤ 64 MiB, plus lopdf's re-decode of the accepted streams (≤ 64 MiB). At most one decoded stream and lopdf's parse of it are alive at a time (≈ 100 MiB transient). This is counted in the C0 page-text working set.
- **Unit heading:** `--- page N · text_layer ---`, `--- page N · ocr_layer (text embedded by OCR software, may contain recognition errors) ---`, `--- page N · no text layer (scanned image) ---`, `--- page N · empty ---`, and for `content_too_large` `--- page N · text not extracted (page content exceeds the extraction limits) ---` (content, work, glyph-output or `q` limit; ledger STRUCT-1, Ф2-F4-B1 extension). If suspicious, append ` · suspicious: <reason>`. Ф3 appends the channel-dependent view hint. Locator: `{"page":N,"source":"text_layer"|"ocr_layer"}`, or `{"page":N,"kind":"no_text"|"empty"}`, plus `"suspicious":reason`, plus `"contentTooLarge":true` on a flagged page.
- **`unit_range`:** `startPage`/`endPage` (1-based, inclusive) give `PAGE_OUT_OF_RANGE` if outside `1..=page_count`.
- **Inspect JSON:** `{"pageCount","encrypted","producer","title","pages":{"text":"1-12","ocr_text":"","no_text":"13-14","empty":""},"suspicious":{"no_cyrillic_over_scan":"20"},"contentTooLarge":"14","classified":N,"complete":bool,"nextCursor"?}`. `contentTooLarge` gives the `page_ranges` of flagged pages (`""` when none); those pages also appear under `no_text`. It stops at the deadline after at least one page, also inside a page (C7 deadline rule; the interrupted page is classified by the next call), and returns an `Inspect` cursor (`u` = next page index). A resumed call reports only the newly classified pages, with `"fromPage"`.

    - XLSX: before `worksheet_range(name)`, run `Xlsx::worksheet_cells_reader(name)` (calamine 0.36.1, inherent on `Xlsx`) and stream `next_cell()` to compute the min/max row and column of the cells; if `(rows × columns)` > `SHEET_CELL_LIMIT`, return `FILE_TOO_LARGE` ("sheet range too large") without building the range. The reader holds one cell at a time.
    - XLSX expanded text, in the same pass: `next_cell()` yields `DataRef::SharedString(&str)` borrowing calamine's shared-string table (no copy), while `worksheet_range` later clones that string into every referencing cell. So the pre-scan sums the byte length of every text-carrying cell value (`SharedString`, `String`, `DateTimeIso`, `DurationIso`), counting each shared-string reference separately. If the sum exceeds `SHEET_TEXT_LIMIT`, return `FILE_TOO_LARGE` ("sheet text too large") before `worksheet_range` is called.
    - XLS: calamine parses every sheet at open and pre-reserves from the BIFF `DIMENSIONS` record (`0x0200`), so before `open_workbook_from_rs`, read the `Workbook` (else `Book`) stream with `cfb` through `take(SHEET_LIMIT)` into memory and walk its records (u16 type, u16 length): the globals from offset 0 to the first `EOF`, then, as calamine does, one sheet walk per `BOUNDSHEET8` (`0x0085`) entry, from its `lbPlyPos` to the end of the next `EOF` record (or the stream end). calamine parses a substream once per entry that names it, so each byte must be parsed at most once: an `lbPlyPos` outside the stream, or a sheet substream that is identical to, or overlaps, another entry's substream or the globals substream (offset 0 to the end of the globals `EOF`), returns `DOCUMENT_INVALID` ("overlapping sheet substreams") before `open_workbook_from_rs`. For each sheet walk, take the extent from `DIMENSIONS` and from the row/column of cell records (`0x0203`, `0x0204`, `0x00FD`, `0x027E`, `0x00BD`/`0x00BE` with their last column, `0x0006`, `0x0201`, `0x0205`, `0x00D6`). If the larger of the two extents, summed over all sheet walks, exceeds `SHEET_CELL_LIMIT`, return `FILE_TOO_LARGE`.
    - XLS expanded text, in the same record walk: calamine's `parse_label_sst` clones the SST string into every `LABELSST` cell. So the walk first parses the globals `SST` record (`0x00FC`, continued by `0x003C` `CONTINUE` records, including strings split across a `CONTINUE` boundary with a new flags byte) into a table of per-string upper-bound byte lengths (`cch × 3`, the most UTF-8 bytes one UTF-16 unit can decode to; rich-text runs and ext data are skipped, not stored). The table is a `Vec<u32>` of at most `SHEET_TEXT_LIMIT / 48` entries; one more entry returns `FILE_TOO_LARGE` ("too many shared strings"), because calamine's own SST `Vec<String>` costs 24–48 bytes per entry of as little as 3 stream bytes. Then every `LABELSST` (`0x00FD`) adds the length of the referenced entry (an out-of-range index → `DOCUMENT_INVALID`), and `LABEL` (`0x0204`), `RSTRING` (`0x00D6`) and formula `STRING` (`0x0207`) records add their own `cch × 3`. If this sum plus the formula charges (next bullet), over all sheet walks, exceeds `SHEET_TEXT_LIMIT`, return `FILE_TOO_LARGE` ("sheet text too large") before `open_workbook_from_rs`.
    - XLS formula text, in the same record walk: calamine's `parse_formula` builds a `String` for every `FORMULA` record (`0x0006`) of every sheet at open, expanding 3-D references to sheet names and `PtgName` to defined-name text. The globals walk also records `max_sheet` = the largest `cch × 3` over `BOUNDSHEET8` names (at least 4, for `#REF`) and a `cch × 3` bound per `NAME` (`0x0018`) record, in record order (calamine's defined-name order). For each `FORMULA` record, the walk tokenizes `rgce` (`cce` = u16 at data offset 20, tokens from offset 22), consuming each ptg with the byte sizes calamine 0.36.1 `parse_formula` uses for the workbook's BIFF version, and adds an upper bound of the text that token produces:
      - 3-D tokens (`0x3A`–`0x3D`, `0x5A`–`0x5D`, `0x7A`–`0x7D`): `max_sheet + 32` (sheet name, `!`, and a reference of ≤ 23 chars: columns up to 4 letters, rows up to 5 digits);
      - `PtgName` (`0x23`/`0x43`/`0x63`): the referenced `NAME` entry's bound (5, for `#REF!`, when out of range);
      - `PtgStr` (`0x17`): `cch × 3 + 2`; `PtgAttrSpace` (`0x19` with `0x40`/`0x41`): its `cch` (inserted spaces); `PtgNum` (`0x1F`): the exact length of the f64's `{}` rendering (up to ~330 chars, since there is no exponent), counted through a length-only `fmt::Write`;
      - `PtgFunc`/`PtgFuncVar`: `20 + argc` (the longest `FTAB` name is 18 chars, plus parentheses and commas; `argc` as calamine reads it, ≤ 255);
      - other references (`PtgRef`/`PtgArea` and their error forms): 24; `PtgErr`, `PtgBool`, `PtgInt`, `PtgArray`, `PtgNameX`, `PtgAttrSum`: 13 (the longest is `#GETTING_DATA`); operators, unary operators, `PtgPercent` and `PtgParen`: 2; `PtgExp`, `PtgMissArg`, `0x18` and the other `PtgAttr` forms: 0;
      - an unknown ptg, or a token that runs past `cce`, ends that record's tokenization (calamine then drops the partial string and stores the fallback message below).
      The sum of these per-token bounds is the record's `token_bound`. **Per-record charge:** calamine 0.36.1 `parse_formula` (xls.rs:1449) calls `String::with_capacity(rgce.len())` *before* it restricts the input to `cce`, and `Range::from_sparse` moves that `String` into the formula range without shrinking it. Here `rgce` is everything from data offset 20 of the record as calamine's `RecordIter` delivers it, i.e. including the data of immediately following `CONTINUE` (`0x003C`) records, which it appends. So every `FORMULA` record of every sheet walk is charged `rgce.len() + 2 × token_bound + 256`, whether or not tokenization succeeded: the full initial reservation, growth by doubling past it (capacity ≤ 2× the text), and a fixed 256 bytes for the `Unrecognised formula for cell (r, c): <error>` string calamine stores whenever `parse_formula` returns an error (unknown ptg, empty operand stack, `InvalidFormula` stack mismatch, including `cce = 0`; the message is ≤ ~100 chars, which `format!` grows to ≤ 144 bytes of capacity).
      The worst case per input byte is a 3-D token (≤ 7 + 2 × 797 bytes charged for 7 rgce bytes, ≈ 229×); padding after `cce` is charged byte for byte through `rgce.len()`, and the 256-byte fallback allowance applies per record of ≥ 24 stream bytes. All of it is counted before calamine allocates. Transient copies inside one formula (`split_off` for operators and functions) are at most 2× that formula's bound.
    - XLS container: if the pre-scans pass, the bytes read above are written as the single stream `Workbook` into a new in-memory CFB (`cfb::CompoundFile::create(std::io::Cursor<Vec<u8>>)`, `create_stream`, `flush`, `into_inner`), and calamine opens that copy as `Source::Memory`, never the original file. calamine's own CFB reader calls `Vec::with_capacity` with the header's FAT-sector count (offset 44) and with a u32 it reads at offset 62, and it follows sector chains without loop detection. In the copy, those counts and chains are written by the `cfb` crate for one stream ≤ `SHEET_LIMIT`, so they stay small and consistent, and the stream calamine parses is exactly the one the pre-scans walked. Memory: the copy ≤ `SHEET_LIMIT` + CFB overhead; the pre-scan buffer is dropped before calamine opens.

- **EML:**

- **Addressing:** `path` = `<disk path>("::"<member>)*` (≤ `CONTAINER_DEPTH`). `relative()` keeps rejecting `:`, so `::` is split off before the disk part is validated.
  - ZIP member: its normalized name. EML/MSG attachment: the decimal 1-based index (`letter.eml::2`).
  - Each member's format comes from its own name (attachments: the attachment file name). `blocked()` applies to every member path.
  - A member whose raw name normalizes to `None`, or that is encrypted, or uses a method other than Stored/Deflated, is listed with `readable:false` and a `reason`. Reading it returns the matching error.
  - Member read: declared `size() ≤ min(MEMBER_LIMIT, format limit)`; declared ratio ≤ `ZIP_RATIO_LIMIT` when > 1 MiB; actual bytes read through `take(declared + 1)`, and exceeding the declared size returns `ZIP_INVALID`.
  - Nested containers are opened from `Source::Memory`.
- **Container listing:** `list_directory` on a container uses the same entry shape (`name`, `path` = display, `relativePath`, `type` file/directory, `size`) plus `compressedSize`/`readable`/`reason` for ZIP and `index`/`mimeType` for attachments. Directories implied by member paths are synthesized; `depth` counts `/` levels below the given prefix. The cursor is `Walk` with `p` = member components.
- **Document search:**
  - `search_text` folder mode visits files in walk order. Text uses today's path. Pdf/Docx/Xlsx/Xls/Eml/Msg up to `SEARCH_DOC_FILE_LIMIT` use `find_in_document` with `max_hits = 1`. Other formats are skipped.
  - Unfinished documents: if `find_in_document` stops at the deadline (or another per-call budget) and returns a position, the file is not advanced past. The `Walk` cursor gets `p` = that document's components, `f` = its fingerprint and `(u, o)` = the returned position. The next call builds the `Walker` with `include_resume_entry = true`, so the document is re-found by comparing names read from disk (the cursor never opens a path). It resumes `find_in_document` at `(u, o)` when the fingerprint still matches, or at unit 0 when the file changed. The walk moves past the file only after a hit (one match per file) or exhaustion. Each call processes at least one unit (progress guarantee), so no prefix is re-searched endlessly. If the document is gone, the walk continues with the next entry.
  - A result gets `"locator"` and a snippet prefixed `[p. N]`, `[sheet «S» row R]`, `[¶N]` or `[mail]`. The response adds `documentsSearched`.
  - `DOC_SCAN_LIMIT` counts the source bytes read.
  - Single-document mode (`path` resolves to a file or member) returns all hits up to `limit` and continues with a `Find` cursor `(u, o)`.

## Test strategy

General rules for every phase: run the gate commands from Global Constraints, plus `python3 -B -m unittest test/test_mcp_experiment.py` (Ф1 onward). All fixtures are synthetic: built in Rust test code (in memory or `tempfile`) or in `test/native.test.mjs` inside its temp fixture dir. **Never** read, copy or quote files under `Work (local)` in automated tests. ## Risks / unknowns / assumptions

- Ф1 — SECURITY: Step 4's probe generator builds output file paths (the probe folder, the probe files inside it and the answers file) from the CLI-supplied `<new-dir>` and `--answers` arguments, which the code does not control (Step 4 already refuses existing targets).
- Ф2 — SECURITY: Step 3 decodes client-supplied continuation cursors (deserialized untrusted input that steers traversal). Step 2 refactors the capability-based open path (`RootDir::open_file`) used by every read. Step 6 parses untrusted PDF bytes with lopdf (decompression bombs, malformed objects, recursion, and `Content::decode` memory amplification, bounded per page by `PDF_CONTENT_LIMIT`).
- Ф3 — SECURITY: Steps 2–4 decode untrusted image formats and PDF image streams (JPEG/PNG/TIFF/CCITT/raw samples with attacker-chosen dimensions), and Step 4 rebuilds a new PDF from untrusted objects.
- Ф4 — SECURITY: Steps 1–4 parse untrusted DOCX (ZIP + XML), XLSX/XLS (calamine), EML (MIME, charsets) and MSG (CFB) data.
- Ф5 — SECURITY: Steps 1–3 build logical paths from untrusted archive member names and attachment indexes, and decompress untrusted ZIP members (zip bombs, name-based escape, nested containers).
- **R1 — ChatGPT may not deliver images (high probability).** An OpenAI staff reply on the community forum (22 Apr 2026, thread "ChatGPT connector returns empty {} for MCP tool results with type: image") says image blocks are valid MCP but are not currently a model-visible vision path, and that image-only results show as `{}`. Mitigation: Ф1 measures it. Every image/binary result carries a text block. Branch C keeps the server lightest (no `image` crate) and still delivers all text features.
- **R2 — Response-size ceiling unknown** (ChatGPT, tunnel-client, JSON-RPC line size). Mitigation: probes C1–C6 in Ф1. `OUTPUT_LIMIT`, `IMAGE_OUTPUT_LIMIT` and `PAGE_PDF_OUTPUT_LIMIT` are calibrated, not guessed.
- **R3 — Reliance on lopdf loading semantics** (filter applied per object; empty streams re-read; no rayon). Verified by reading the lopdf 0.45.0 source and compiling the filter during planning. Mitigation: the placeholder unit test fails loudly if semantics change. Keep the requirement `lopdf = "0.45"`.
- **R4 — Memory on huge PDFs.** Synthetic measurement: 326 MiB → 354 MB peak RSS filtered. Real files may have many more objects. Mitigation: the `large_pdf_budget` ignored test plus optional manual measurement on the real 330 MB file. If peak RSS > file + 128 MiB or time > 10 s, the implementer lowers `PDF_LIMIT` and records why. Encrypted PDFs use ~2× memory, hence `PDF_ENCRYPTED_LIMIT`.
- **R5 — Text-extraction quality** (missing ToUnicode, Identity-H without a CMap, odd layouts, rotated text). Mitigation: classification flags `undecodable`. The page view and `inspect` let the model fall back to the image. Quality is checked manually on the PDFsharp/iTextSharp/Adobe Scan samples (metadata only: chars per page, kinds).
- **R6 — Parser panics and stack overflows.** Panics are converted to `DOCUMENT_INVALID` by `guarded` (`panic = "abort"` must never be introduced). Stack overflow aborts the worker and cannot be caught, so mitigate with our own recursion limits (forms ≤ 3, containers ≤ 3) and lopdf's `MAX_NESTING_DEPTH`. The tunnel-client restarts the worker on exit; that recovery path is unverified.
- **R7 — calamine cannot be capped from outside, so its inputs are bounded before it runs.** A crafted XLSX can inflate beyond its declared sizes, or declare a huge `<sst uniqueCount>` that calamine passes straight to `Vec::reserve` while opening. A crafted extent (or an XLS `DIMENSIONS` record) can make calamine allocate a huge `Range`. A crafted XLS can also declare huge CFB header counts, which calamine's own CFB reader passes to `Vec::with_capacity`, or have sector chains that loop. And calamine builds and keeps a formula `String` for every XLS `FORMULA` record at open, reserved at the record's full `rgce.len()` (not `cce`) and never shrunk, or replaced by an "Unrecognised formula …" message on error; several `BOUNDSHEET8` entries naming one substream would multiply that. Mitigation (C10): calamine only opens containers we wrote. XLSX parts are inflated by our code through `take()` into a Stored in-memory copy capped at `XLSX_UNPACKED_LIMIT` (actual bytes), with `count`/`uniqueCount` stripped from `sharedStrings.xml`, so calamine never inflates attacker data and never reserves from an attacker count. The XLS `Workbook` stream is re-wrapped in an in-memory CFB written by the `cfb` crate. Sheet extents are pre-scanned (XLSX cell reader, XLS BIFF records, one walk per `BOUNDSHEET8` entry; identical or overlapping sheet substreams return `DOCUMENT_INVALID`, so each byte is parsed once) against `SHEET_CELL_LIMIT` before any `Range` is allocated. Because calamine copies a shared string into every cell that references it (`worksheet_range` for XLSX, `parse_label_sst` for XLS), the same pre-scan sums expanded cell-text bytes per reference, plus a per-`FORMULA` charge of `rgce.len() + 2 × token_bound + 256` (initial reservation, growth, error-message fallback), against `SHEET_TEXT_LIMIT` before those allocations happen. Other count-driven reservations checked in calamine 0.36.1's XLSX/XLS open path and `worksheet_range`: `cells.reserve` in `worksheet_range_ref` (only when the declared dimension is below 100 000), `HashMap::with_capacity(zip.len())` (our copy, ≤ `ZIP_ENTRY_LIMIT` entries), XLS `cells.reserve(rows × cols)` from `DIMENSIONS` (≤ `SHEET_CELL_LIMIT` via the pre-scan), XLS `String::with_capacity(cch)` (u8/u16 `cch`), XLS `parse_formula`'s `String::with_capacity(rgce.len())` (charged in full per record by the pre-scan), and the `RRTabId` reserve (≤ record length). All of these are bounded by the measures above or by constants. Residual: the shared-string table does not scale with input bytes (an empty `<si/>` costs 5 bytes of XML but 24–48 bytes of table). It is bounded instead by the `SHEET_TEXT_LIMIT / 48` entry cap (≤ `SHEET_TEXT_LIMIT` of `String` headers), plus the string bytes themselves (≤ the inflated part or the stream). Cell vectors scale with the bounded cell count. Panics become `DOCUMENT_INVALID`.
- **R8 — ZIP name encodings.** CP866 is the norm for Windows-Explorer zips in Russian locales. The 1251 fallback is a heuristic, and wrong guesses only affect display names. Verified that zip 8.6 replaces raw names with the Info-ZIP Unicode Path field when present.
- **R9 — Binary size.** The full dependency set compiled alone came to a 4.2 MB release binary (the current `local-files` is 5.2 MB), so expect roughly +3–4 MB in total, less in branch C (no `image`/`tiff`/`fax`). There are minor duplicates (`miniz_oxide` 0.8/0.9, `weezl` 0.1/0.2). There are no C or `-sys` crates (checked with `cargo tree`).
- **R10 — MSG parsing has no real samples** (the user has none). Tag numbers come from MS-OXPROPS. The implementer cross-checks each tag against the spec and covers both `001F` and `001E` strings.
- **R11 — Deterministic order and non-UTF-8 names.** Names are compared as `to_string_lossy` strings. Invalid UTF-8 names (impossible on APFS, rare on NTFS) could be revisited or skipped across cursors. Documented.
- **R12 — Search cost.** Folder-wide document search re-parses files on every call (no index by design). It is bounded by `DOC_SCAN_LIMIT`, the per-file limit and the deadline, with a cursor. Large scanned PDFs are skipped by size.
- **R13 — Windows has no OS sandbox**, so parser bugs are exposed only to code-level limits. All readers work on memory/`Read+Seek` and never write.
- **R14 — Tool schema changes** require the user to refresh the connector's tools in ChatGPT (README already says so). Ф1's procedure includes it.
- **R15 — Cloud placeholders** (OneDrive/iCloud "dataless" files) download on read, so a single read may exceed time expectations. Budgets are checked between files, not mid-read.
- **R16 — The image crate's CMYK/odd JPEG handling and EXIF writing for tests** are not verified here. If a synthetic EXIF fixture is impractical, the implementer documents a test seam instead.
- **R17 — Known residual: the lopdf PDF load has no whole-load budget for crafted files (finding Ф2-F5-B2, accepted by the user 2026-10-19; ledger Ф2-F5-B2-doc).** `load_mem_with_options` caps each decoded stream at `PDF_STREAM_LIMIT`, but nothing caps the parsed object set. (a) lopdf `ObjectStream::new_with_limit` (`object_stream.rs:89-116`) parses every `(id, offset)` pair of an object stream on its own and keeps each result, with no check for overlapping or duplicate offsets. So many ids pointing at one large object each keep a copy. Source-derived example, not measured: 4 096 ids pointing at one 1 MiB string compress to 11 574 bytes, inflate to 1 076 350 (under `PDF_STREAM_LIMIT`), and imply ≈ 4 GiB of retained copies. (b) Parsing amplifies up to ≈ 60×: `size_of::<lopdf::Object>()` is 120 bytes, e.g. for each element of a flat array of short numbers. (c) `PDF_STREAM_LIMIT` is per stream, not cumulative. (d) Duplicate xref offsets cost CPU for each entry. (e) Encrypted PDFs bypass the load filter (`load_encrypted_document`). They are bounded by `PDF_ENCRYPTED_LIMIT` when the raw pre-check (C7 Loading step 1) sees `/Encrypt`; a `#xx`-escaped key (e.g. `/Encr#79pt`) passes that check, so such a file is loaded on the encrypted path up to `PDF_LIMIT` (512 MiB) before the post-load check rejects it (ledger Ф2-F6-N2). An allocation failure aborts the worker, since `guarded` catches panics, not OOM (R6). The C0 memory figures therefore hold for ordinary PDFs only. Accepted for Ф2 with no code requirement. A whole-load guard is revisited before Ф5 (Non-goals), because Ф5 `search_text` parses PDFs folder-wide.
- **A1 — Assumption:** `cap_std::fs::File` implements `Read + Seek` (verified in cap-std 4.0.3), so ZIP/CFB/TIFF/calamine can stream from disk without full reads.
- **A2 — Assumption:** the user's runtime is the installed app. The experiment installs the dev build with the existing DMG installer, which backs up the release app automatically. Version stays 2.1.2 until Ф5.
