# Чтение и поиск TXT в Windows-1251

## Цель

В Strigov Local MCP 2.2.0 русский TXT, который КонсультантПлюс экспортирует в Windows-1251 без BOM и с переводами строк CRLF, не читается. На native Windows HPC `read_text_file`, `read_file`, `read_document`, `fetch` и `search_text` по пути файла возвращают `NOT_TEXT`, а `search_text` по папке молча пропускает файл при `skippedInaccessible=0` (`artifacts/cp1251-hpc-20261030/REPORT.txt`, `results.json`). Причина — строгая проверка UTF-8 в трёх местах: `native/filesystem.rs:518` (чтение по строкам), `native/documents.rs:555` и `:602` (`PlainText`) и `native/filesystem.rs:786` (поиск по папке). После исправления для текстовых форматов действует одно общее правило: сначала UTF-8, как сейчас, затем fallback на Windows-1251 только для текстовых расширений с двумя детерминированными отказами: по BOM UTF-8 и по явно перечисленным управляющим байтам. Статистической эвристики нет, поэтому защита от бинарных и повреждённых данных неполная; остаточная неоднозначность описана в «Дизайне». Все пять методов и поиск по папке должны давать одинаковый текст и номера строк; UTF-8, лимиты, диапазоны строк, `maxChars`, курсоры и правила доступа не меняются. Готовность подтверждают behavioral RED до правок production-кода, локальные регрессионные проверки и GREEN на native Windows HPC на изолированном snapshot.

## Вне скоупа

- Универсальное автоопределение кодировок. KOI8-R, CP866, ISO-8859-5, Windows-1252/Latin-1, Mac Cyrillic, UTF-16 и UTF-32 не распознаются. Статистического или языкового анализа нет. Однобайтовый текст в другой кодировке, прошедший защиту, читается как Windows-1251 (с неверными буквами) и помечается `encoding:"windows-1251"`.
- Распознавание повреждённого UTF-8 без BOM, бинарных данных без запрещённых байтов и UTF-16/UTF-32. Такие файлы читаются как Windows-1251 с `encoding:"windows-1251"` или, если они являются корректным UTF-8, как UTF-8 в 2.2.0. Повреждённый UTF-8 без BOM в 2.2.0 давал `NOT_TEXT`, а теперь читается как Windows-1251 с кракозябрами. Это осознанное изменение (AC12, AC27).
- Чтение объявлений кодировки: XML prolog, HTML `<meta charset>`, MIME-заголовки текстового файла. Новый параметр выбора кодировки у инструментов.
- Любые изменения поведения UTF-8, включая удаление BOM: U+FEFF остаётся в возвращаемом тексте, как в 2.2.0.
- Fallback для файлов, которые не являются текстовым форматом (расширение вне `filesystem::is_text`, например `.dat` или файл без расширения). Бинарная ветка `read_file` (base64 `blob`) не меняется.
- Особая обработка Ctrl-Z (0x1A) в конце DOS-файлов. Корректный UTF-8 имеет приоритет и с управляющими байтами читается как UTF-8, как в 2.2.0: `61 62 63 1A` → `abc\u001A`, `41 00 42` → `A\u0000B`. `NOT_TEXT` получает только файл, который не является корректным UTF-8 и содержит хотя бы один запрещённый байт из точного списка в «Дизайне» (0x00–0x08, 0x0B, 0x0E–0x1F, 0x7F, 0x98), в том числе 0x1A. TAB, LF, FF и CR в fallback разрешены.
- Неразличение «е» и «ё» при поиске. Регистр Ё/ё по-прежнему учитывается без различия, как и раньше.
- Поиск внутри ZIP и вложений при обходе папки, имена файлов в архивах (CP866/CP1251 уже поддержаны в `native/archive.rs`), legacy Node-сервер `src/`.
- Изменение лимитов, формата курсоров, правил доступа, кодов ошибок и подсказки `documents::unsupported`.
- Повышение версии (`Cargo.toml` остаётся 2.2.0), сборка дистрибутивов, релиз, push, установка или обновление приложения на macOS и HPC.
- Проверка на 66 реальных TXT пользователя (они не получены), а также через ChatGPT и туннель.

## Дизайн

### Правило декодирования

Одно правило для всех путей. Это проектное решение без статистики; его границы фиксируют negative controls из AC12–AC14 и контрпримеры из AC26–AC27.

1. **Текстовый формат** — тот же, что сейчас: `filesystem::is_text(path)`, то есть `Format::Text` в `documents::format_of`. Для элементов ZIP и вложений писем формат определяется по имени элемента, как сейчас. Fallback разрешён только текстовым форматам (`legacy = true`). Для прочих форматов в `read_text_file` и в текстовой ветке `read_file` действует только UTF-8 (`legacy = false`).
2. **Решение принимается для всего файла.** Построчного переключения кодировки нет.
3. **Порядок проверок:**

| № | Содержимое | Результат |
|---|---|---|
| 1 | Весь файл — корректный UTF-8 (включая пустой файл, ASCII и UTF-8 с BOM) | UTF-8, как в 2.2.0, `encoding:"utf-8"`, U+FEFF остаётся в тексте |
| 2 | Не UTF-8 и `legacy = false` | `NOT_TEXT`, `File is not valid UTF-8. Use read_document for document formats.` (как сейчас) |
| 3 | Не UTF-8 и первые три байта файла — `EF BB BF` | `NOT_TEXT`, `File looks like damaged UTF-8`: BOM объявляет UTF-8 |
| 4 | Не UTF-8 и в файле есть хотя бы один запрещённый байт | `NOT_TEXT`, `File is neither UTF-8 nor Windows-1251 text` |
| 5 | Иначе | Windows-1251 для всего файла, `encoding:"windows-1251"` |

Других проверок нет: ни подсчёта многобайтовых последовательностей, ни частот букв, ни языкового анализа. BOM UTF-16/UTF-32 (`FF FE`, `FE FF`) правилом не проверяется.

- **Запрещённые байты** для Windows-1251: 0x00–0x08, 0x0B, 0x0E–0x1F, 0x7F и 0x98. Разрешены TAB, LF, FF и CR. Байт 0x98 в CP1251 не определён: `encoding_rs` 0.8.42 отображает его в управляющий символ U+0098 (проверено по `windows_1251` в `encoding_rs/src/data.rs`), а Python-кодек `cp1251` его не кодирует.

Декодирование выполняет `encoding_rs::WINDOWS_1251.decode_without_bom_handling` — крейт уже в зависимостях: `Cargo.toml` `encoding_rs = "0.8"`, используется в `native/archive.rs`, `native/email.rs` и `native/msg.rs`. Однобайтовая таблица не даёт ошибок декодирования, поэтому отказ возможен только по правилам 3 и 4, и только для описанных в них байтов.

Неоднозначные и повреждённые данные:

| Случай | Поведение |
|---|---|
| CP1251-файл, который одновременно является корректным UTF-8 | UTF-8 имеет приоритет. Это возможно, только если в файле нет байтов `C0`, `C1` и `F5`–`FF` («А», «Б», «х»–«я»: в UTF-8 они не встречаются никогда), а каждый байт `C2`–`F4` («В»–«Я», «а»–«ф») начинает корректную последовательность с байтами `80`–`BF`. Пример: `C2 BB` («В»») читается как `»` (`utf8-also-cp1251.txt`). Одна некорректная последовательность в любом месте переводит весь файл в CP1251: в `cp1251-nbsp.txt` пары `C2 A0` корректны, но `97` нет (AC26) |
| UTF-8 с повреждённым байтом или обрезанной последовательностью, без BOM | Если запрещённых байтов нет, весь файл читается как Windows-1251 с кракозябрами и `encoding:"windows-1251"` (`damaged-utf8.txt`, `truncated-utf8.txt`, AC12). В 2.2.0 был `NOT_TEXT`. По байтам такой файл неотличим от CP1251: `text: ` + `D1` — это и обрезанное «С» в UTF-8, и «text: С» в CP1251 |
| Смесь UTF-8 и CP1251 в одном файле | Весь файл читается как CP1251, UTF-8-фрагменты становятся кракозябрами |
| KOI8-R, CP866, Latin-1 без запрещённых байтов | Читается как Windows-1251 с неверными буквами, `encoding:"windows-1251"`. CP866 с «Ш» (0x98) получает `NOT_TEXT` |
| UTF-16 | Отказ только при запрещённом байте. Любой символ U+0000–U+08FF (пробел, CRLF, латиница, кириллица) имеет байт 0x00–0x08, поэтому обычный UTF-16-текст получает `NOT_TEXT` (`utf16.txt`, AC13). Текст только из символов вне этого диапазона может пройти: `FF FE AC 20` (BOM и «€») читается как `яю¬ ` (AC27). Корректный UTF-8 из таких байтов читается как UTF-8 |
| UTF-32 | Каждый символ содержит `00`, поэтому файл либо является корректным UTF-8 с NUL и читается как в 2.2.0 (например, ASCII в UTF-32LE), либо получает `NOT_TEXT` |
| Бинарные данные с текстовым расширением | Отказ только по правилам 3–4. `bytes(range(256))` получает `NOT_TEXT` и при поиске по папке учитывается в `skippedInaccessible`. Данные без запрещённых байтов читаются как Windows-1251: `B8 FF FF FF FF C3` → `ёяяяяГ` (AC27). Корректный UTF-8 с NUL и другими управляющими символами читается как UTF-8, как в 2.2.0: `41 00 42` → `A\u0000B` (AC27) |
| Файл изменился между проходами | Сохраняются проверки роста (`FILE_TOO_LARGE`) и отпечатка (`STALE_CURSOR`). Каждая строка повторно проверяется при декодировании; при нарушении выбранной кодировки — `NOT_TEXT` |

Примеры применения правила (проверены через Python `bytes.decode`):

| Байты | Правило | Результат |
|---|---|---|
| Текст RED-пробы в CP1251 (`cp1251.txt`) | 5 | Windows-1251 |
| `C2 A0 32 30 32 34 2C 20 C2 A0 32 30 32 35 20 97 20 31 30 30` (`cp1251-nbsp.txt`) | 5 | `В\u00a02024, В\u00a02025 — 100` |
| `C2 BB` (`utf8-also-cp1251.txt`) | 1 | UTF-8 `»` |
| `EF BB BF` + CP1251 (`bom-cp1251.txt`) | 3 | `NOT_TEXT` |
| UTF-8 с `FF` после первого CRLF (`damaged-utf8.txt`, 193 байта, без `98` и управляющих байтов) | 5 | Windows-1251, кракозябры |
| `74 65 78 74 3A 20 D1` (`truncated-utf8.txt`) | 5 | `text: С` |
| `B8 FF FF FF FF C3` (`ambiguous-bytes.txt`) | 5 | `ёяяяяГ` |
| `FF FE AC 20` (`utf16-no-ascii.txt`) | 5 | `яю¬ ` |
| `FF FE` + UTF-16LE текста RED-пробы (`utf16.txt`) | 4 | `NOT_TEXT` |
| `41 00 42` (`utf8-nul.txt`) | 1 | UTF-8 `A\u0000B` |

### Новый модуль `native/text.rs`

```rust
#[derive(Clone, Copy, Debug, PartialEq, Eq)]
pub(crate) enum TextEncoding { Utf8, Windows1251 }
impl TextEncoding {
    pub(crate) fn label(self) -> &'static str; // "utf-8" | "windows-1251"
}

/// Решение о кодировке всего файла; куски должны заканчиваться на b'\n' или на конце файла.
pub(crate) struct Detector { /* legacy, first, bom, utf8_ok, forbidden_seen */ }
impl Detector {
    pub(crate) fn new(legacy: bool) -> Self;
    pub(crate) fn feed(&mut self, chunk: &[u8]);
    pub(crate) fn finish(&self) -> Result<TextEncoding>; // правила 1–5, ошибки NOT_TEXT
}

/// Потоковый проход: читает не больше size+1 байт по строкам (read_until b'\n'),
/// при росте файла — FILE_TOO_LARGE "File grew beyond the read limit";
/// возвращает кодировку и число строк (1 + число '\n').
pub(crate) fn scan<R: BufRead>(reader: R, size: u64, legacy: bool) -> Result<(TextEncoding, usize)>;

/// Декодирует уже классифицированные байты; повторно проверяет UTF-8 или запрещённые байты.
pub(crate) fn decode(encoding: TextEncoding, bytes: &[u8]) -> Result<Cow<'_, str>>;

/// Решение и декодирование для буфера целиком (поиск по папке).
pub(crate) fn decode_buffer(bytes: &[u8], legacy: bool) -> Result<(Cow<'_, str>, TextEncoding)>;
```

Подача файла построчно и целиком даёт одинаковое решение: 0x0A не входит ни в одну многобайтовую последовательность UTF-8, поэтому файл корректен как UTF-8 тогда и только тогда, когда корректен каждый кусок (`std::str::from_utf8`); BOM целиком находится в первой строке, а запрещённые байты проверяются побайтно. `Result` и `error` берутся из `crate::filesystem`. В `native/main.rs` добавляется `mod text;`.

### Память и лимиты

- Все константы лимитов сохраняются (AC15), размеры по-прежнему считаются в исходных байтах.
- `read_text_file` и `read_file` для текста теперь читают источник дважды, как `PlainText` уже делает сейчас: проход `scan` и проход вывода. Оба прохода ограничены `TEXT_READ_LIMIT` (64 МиБ).
- Результат декодирования CP1251 занимает не больше 3 байт UTF-8 на исходный байт (`№` и `—` занимают 3 байта, кириллица — 2):
  - чтение по строкам декодирует одну строку;
  - поиск по папке декодирует файл не больше `TEXT_LIMIT` (5 МиБ), то есть результат не больше 15 МиБ.
- Худший случай — файл 64 МиБ в одну строку в `read_document`: исходная строка плюс декодированная занимают до 256 МиБ. Это ограниченный остаточный риск в рамках принятой модели угроз; бюджеты DOCX и XLSX того же порядка.
- Проверка UTF-8, BOM и запрещённых байтов линейна и выполняется в том же проходе, что и сейчас проверка UTF-8.

`TYPO = '«Определение Судебной коллегии» — дело № 305-ЭС22-2377…\r\nУчёт: ЁМКОСТЬ, ёмкость; „цитата“ – § 3,\u00a0стр. 2\r\nЁлкин А.Ё. и ёлкин а.ё.\r\n'`

### Решения, принятые без отдельного вопроса

1. Единственный fallback — Windows-1251. Он разрешён только для текстовых расширений, если файл не начинается с BOM UTF-8 и не содержит запрещённых байтов.
2. Кодировка определяется для всего файла. BOM `EF BB BF` требует строгого UTF-8.
3. Статистической эвристики нет. Повреждённый UTF-8 без BOM читается как Windows-1251 с кракозябрами и `encoding:"windows-1251"`, а не `NOT_TEXT`, как в 2.2.0: надёжно отличить его от CP1251 по байтам нельзя.
4. Нечитаемые текстовые файлы в поиске по папке учитываются в существующем `skippedInaccessible`, без нового поля — по образцу отвергнутых документов.
5. `encoding` добавляется всегда для простого текста, U+FEFF не удаляется, код ошибки остаётся `NOT_TEXT`.
6. `read_text_file` и `read_file` используют тот же двухпроходный `scan`, что `PlainText`, — одна точка решения для всех методов.
7. Snapshot для HPC передаётся `git bundle` локального коммита. Версия не повышается, ничего не публикуется и не устанавливается.
